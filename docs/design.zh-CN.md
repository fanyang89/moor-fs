# nas-fs 分布式文件服务设计

状态：初步设计，尚未实现。本文记录已确认的产品约定，并明确需要原型验证的技术细节。

## 1. 目标与范围

将局域网内容量不同的 NAS 通过 SMB 纳入统一存储池，由多个接入节点提供一致的 SMB 共享目录。

已确认的需求：

- 每个接入节点都能提供文件访问服务，客户端无需安装专用客户端。
- 支持 Windows、macOS 和 Linux 客户端挂载 SMB 共享。
- 面向照片、视频、文档和备份，支持普通文件所需的偏移写、截断和 flush，但不针对数据库、虚拟机磁盘等高频随机写负载优化。
- 文件完整存放在 NAS 上，首版不跨 NAS 分块。
- 默认双副本，支持单副本；双副本必须位于不同物理 NAS。
- 用户可以在 NAS 管理界面将已有文件或目录移动到导入区；系统发现并接管，路径冲突需要明确提示。
- 实现语言采用 Zig，核心依赖自有 grpc-lite 和 raftz。

首版范围之外：多元数据分片、透明 SMB 会话故障接管、重度随机写优化、自动跨地域复制。

## 2. 整体架构

```text
                 局域网 SMB 客户端
                  /      |      \
               节点 A   节点 B   节点 C
               Samba    Samba    Samba
                  |       |       |
                文件系统适配与 nas-fs 服务
                  |               |
                  +-- 元数据组 ---+
                  | raftz，3 副本 |
                  | 本地 LMDB     |
                  |               |
                  +-- SMB 后端访问 --+
                         |          |
                       NAS A      NAS B ...
```

### 2.1 节点角色

- **接入节点**：处理 SMB 文件操作、访问后端、执行导入与恢复任务。
- **元数据节点**：保存权威命名空间、版本、副本位置、写入协调和任务状态。
- **NAS 后端**：通过 SMB 提供文件存储，无需运行 nas-fs 程序。

首版使用一个 Raft 组、三个投票成员，可与接入节点共机部署。增加接入节点不必增加投票成员。元数据 leader 负责协调提交，不中转文件数据。

默认所有接入节点都能访问所有 NAS，避免单个接入节点故障导致某台 NAS 失去入口。

### 2.2 客户端入口

每个节点提供相同共享，例如 `\\node-a\pool`、`\\node-b\pool`。

首版使用明确节点地址。统一域名和接入调度可后续增加；DNS 切换不等于已有 SMB 会话或打开句柄的透明接管。节点故障后，受影响客户端需要重连或重试。

## 3. 技术栈与复用边界

| 组件 | 规划职责 |
| --- | --- |
| Zig | 核心服务实现 |
| grpc-lite | 内部 RPC 与 raftz 的传输能力 |
| raftz | 元数据共识、日志复制与状态机编排 |
| LMDB | 本地已应用元数据状态，默认同步事务 |
| Samba | SMB 协议、认证与客户端会话 |
| Linux CIFS | 优先作为 NAS SMB 访问方式 |
| FUSE / Samba VFS | 通过原型决定具体组合 |

### 3.1 本地代码检查结论

检查时的 zookeeper-zig 使用 Zig 0.17.0，服务端采用 raftz、grpc-lite 和 RocksDB。其设计将业务变更与 Raft applied index、term 在 RocksDB 同步写批次中原子提交。

`zookeeper-zig/src/server/quorum.zig` 的 `Quorum` 直接持有 `ZooKeeperStateMachine`，不是可直接替换状态机的通用宿主。raftz 已提供独立的 `StateMachine` 接口与 `Raftor` 编排层。

因此，nas-fs 直接实现 raftz 状态机，不依赖或部署 zookeeper-zig，也不将文件映射成 znode。zookeeper-zig 仅作为设计时参考的已有实现，不加入项目依赖或 submodule。

grpc-lite 不自动重放 RPC，nas-fs 必须实现请求标识、结果查询、去重与安全重试。

工具链与依赖版本在实施时重新核对并固定。沿用各依赖的标准获取与校验流程，不修改共享依赖缓存。

## 4. 命名空间与存储布局

客户端看到统一逻辑目录，不暴露文件所在 NAS。目录项通过稳定文件 ID 引用文件，后端对象名不随逻辑路径变化。

每个后端建立专用目录：

```text
nas-fs/
├── import/       用户放入待导入文件
├── staging/      未发布写入、导入接管和恢复数据
└── objects/      已发布对象
```

`objects/` 和 `staging/` 应限制普通用户直接修改。用户通过 NAS 管理界面操作 `import/`，文件接管后通过统一共享管理。

- 逻辑重命名和目录移动只更新元数据，不迁移文件内容。
- 已发布对象不可修改；新内容生成新版本。
- 单个文件必须能完整容纳于每个目标 NAS，存储池总剩余空间不代表单文件可写空间。
- 全部节点使用一致的名称比较规则，同时保留原始显示名称。大小写、Unicode、保留名称及 SMB 名称约束需要在原型中明确。

## 5. 元数据模型与一致性

### 5.1 逻辑记录

| 记录 | 主要内容 |
| --- | --- |
| inodes | 稳定文件 ID、类型、属性、当前版本、期望副本数 |
| dirents | 父目录 ID、规范化名称、显示名称、文件 ID |
| versions | 版本 ID、大小、校验信息与副本列表 |
| replicas | 后端 ID、对象 ID、验证状态 |
| backends | NAS 标识、共享位置、故障域和管理状态 |
| write_sessions | 持有者、写入代次、预期旧版本、工作对象 |
| reservations | 各后端空间预留 |
| operations | 导入、发布、删除、修复等任务状态 |
| requests | 请求 ID、提交结果与去重保留信息 |

具体编码、索引与键布局在实施阶段确定。

### 5.2 提交原则

- 命名空间、版本发布、策略变更与相关任务记录使用同一个元数据事务域。
- 状态机只执行确定性操作，不在 apply 中读取实际时间、扫描 NAS 或执行网络 I/O。
- 业务变更和 applied index、term 原子持久化。
- 权威读取通过线性一致读屏障和本地应用进度检查实现；缓存必须有明确失效规则。
- 超时可能表示结果未知，客户端通过请求 ID 查询或重试，不直接认定事务失败。
- 去重记录设置保留范围，客户端重试必须遵守相应期限。

Raft 多数派不可用时停止元数据变更。已固定版本的读取是否继续，需要同时满足对象引用、句柄与租约有效性，不能无条件放行。

## 6. 副本策略

### 6.1 策略继承

存储池默认两副本；目录可覆盖为一副本或两副本。文件创建或导入时记录有效策略。

- 修改文件内容沿用其已有策略。
- 重命名和移动不自动改变策略。
- 调整目录策略时，可明确选择是否应用到已有文件，由后台任务执行。
- 一副本升为两副本后，在复制完成前显示未达标。
- 两副本降为一副本时，先事务提交保留位置及新策略，再安全回收多余副本。

元数据 Raft 三副本与文件副本数相互独立。

### 6.2 故障域与放置

每个后端配置 `failure_domain`，对应实际物理 NAS。同一 NAS 的多个共享不能充当独立副本。

双副本放置必须选择两个不同故障域，并分别满足空间要求。默认按有效剩余容量及负载选择，允许目录级放置约束。

```text
有效可用空间 = NAS 报告可用空间 - 安全余量 - 尚未完成写入的空间预留
```

空间预留通过元数据事务协调。外部导入、其他 NAS 用户和未知长度写入仍可能消耗额外空间，必须处理真实的空间不足错误。

双副本可用容量不简单等于总空间的一半。例如仅有剩余 4 TB 和 12 TB 的两台 NAS，双副本逻辑增量容量至多约为 4 TB，还需扣除安全余量、工作版本等开销。

### 6.3 严格提交

默认不静默降级。双副本版本只有在两份内容均准备完成、通过一致性校验且完成后端 flush 后，才提交元数据并确认成功。

发布对象、版本映射与客户端确认之间仍存在跨系统事务边界，必须通过持久化操作记录恢复。持久性最终依赖 NAS 正确实现 SMB flush 及其底层存储保证。

写入一份失败时不发布新版本，旧版本继续作为已提交状态。若结果未知，先查询发布事务结果，避免误清理已经提交的对象。

## 7. 文件写入与版本发布

### 7.1 写入流程

```text
分配写入代次、工作对象和空间预留
    → 向各目标副本执行相同的有序偏移写入
    → 完成校验与后端 flush
    → 将对象封存为不可变候选版本
    → 校验写入代次和预期旧版本
    → Raft 提交版本与副本位置
    → 返回提交成功
```

随机偏移写和截断必须纳入最终内容校验，不能将到达顺序的输入字节哈希直接视为最终文件哈希。首版可在封存阶段扫描校验，分段校验与优化方式待验证。

写租约本身不能阻止失联节点继续访问普通 NAS。因此工作对象按写入尝试隔离，已发布对象不可修改；过期节点不能通过代次检查发布自己的对象。

删除、垃圾回收和恢复操作也必须针对精确对象身份执行，不能凭租约超时就删除来源不明的路径。

### 7.2 FLUSH 与后续写入

SMB 句柄可能反复写入、flush、继续写入。成功返回的 flush 必须形成符合副本策略、可恢复的持久化边界。

```text
工作版本 W1 → flush 并发布 V1
                    ↓ 下一次修改
                工作版本 W2 → flush 并发布 V2
```

已发布 V1 不再原地修改；没有后续变更时不创建 W2。修改已有大文件可能需要完整复制，每次发布后再修改也可能引入复制放大。

首版接受整文件版本化的简洁模型，但必须测量大文件多次 flush 和小修改的成本。若不满足普通文件工作流，再设计增量工作区或分块方案。

## 8. SMB 接入语义

### 8.1 基础约定

| 操作 | 首版语义 |
| --- | --- |
| 创建 | 原子创建目录项，同名竞争只有一个成功 |
| 读取 | 在有效协调状态下读取确定的已提交版本 |
| 写入 | 同一文件只允许一个有效写入者 |
| 偏移写、截断 | 支持，作用于工作对象 |
| flush | 满足副本策略并持久提交后返回成功 |
| 关闭写句柄 | 提交剩余变更并释放写入权；失败需反馈或记录 |
| 重命名 | 原子更新命名空间，检查共享访问规则 |
| 替换 | 原子切换目标引用，不暴露部分新内容 |
| 删除 | 逻辑删除与物理回收分离，尊重打开句柄规则 |
| 目录枚举 | 支持分页，并发修改下不承诺整次枚举固定快照 |

首版候选为“多读或单写”的保守模型：已有读者可能阻止写打开，已有写者可能阻止其他读写打开。该限制必须通过常见应用验证；如影响正常保存，则扩展共享访问模型。

### 8.2 协调状态

区分 SMB 会话、打开句柄和写入事务。使用稳定文件 ID 协调，不以路径充当锁身份。租约失效后停止依赖该租约的访问，正在处理的操作也需要有效性检查。

多台 Samba 挂载同一逻辑 FUSE 文件系统，并不会自动具备跨节点共享模式、字节范围锁、删除意图、oplock 和 lease 一致性。

原型需要决定：

- Samba 集群机制与 FUSE 是否能传递并协调所需状态。
- 是否增加 Samba VFS 集成。
- Samba 打开句柄协调与 nas-fs 版本发布代次的职责如何衔接。
- 如何统一用户身份、权限和客户端缓存失效。

不能正确跨节点协调的客户端缓存能力首版关闭。完整 ACL、扩展属性、备用数据流等兼容性另行确认，不预先承诺。

## 9. NAS 原地导入

### 9.1 用户操作

用户将已有目录移动到某 NAS 的 `nas-fs/import/`，相对路径映射到统一共享。

例如 `NAS B:/nas-fs/import/photos/2026/` 导入为 `\\node-a\pool\photos\2026\`。

原文件保留在 NAS B 作为第一份数据。若源与接管目录在支持重命名的同一文件系统内，可避免复制第一份内容；跨卷移动不保证零复制。

### 9.2 发现与接管

使用 SMB 通知降低发现延迟，定期扫描兜底。按后端协调扫描任务，持久化任务记录以避免重复导入。

```text
DISCOVERED → CLAIMED → STAGED → REPLICATING → PUBLISHED
                  ↘ CONFLICT / FAILED / WAITING
```

- 自动导入依据稳定窗口尝试接管，但大小和修改时间稳定并不能证明复制已完成。
- 支持用户确认“已放置完成”后启动导入，适用于复制中的大目录。
- 接管期间要求用户停止修改文件；NAS 本地操作可能绕过 SMB 共享模式限制。
- 检测到变化则暂停或失败，不发布不确定内容。
- 任务记录源路径、目标路径、对象 ID及可获得的文件身份信息，恢复时核对实际状态。
- 原路径被新文件复用且无法可靠区分时，进入待确认状态，不猜测身份。

### 9.3 副本与可见性

默认双副本：接管第一份后复制到另一 NAS，校验并 flush，最后提交元数据。

第二份暂时无法完成时显示“等待副本”，保留已接管文件，不宣称导入完成。用户可以明确改为单副本后完成导入。

目录批量导入逐文件提交并显示进度，不承诺整棵目录原子出现。

### 9.4 冲突

- 同名目录合并处理子项。
- 同路径文件、文件与目录重名、大小写等名称冲突不自动覆盖。
- 用户可选择跳过、重命名后导入或明确确认替换。
- 最终提交仍需事务检查路径冲突，不能仅依赖扫描时检查。
- 失败、冲突和等待状态的文件不自动删除。

## 10. 修复、巡检与回收

### 10.1 副本修复

```text
发现副本不足 → 分配任务与空间 → 固定健康源版本
    → 复制到新故障域 → 校验并 flush → 条件提交副本位置
```

提交时重新核对文件版本、策略和任务代次，防止旧版本副本被挂到新版本上。复制期间持有源对象引用，避免被提前回收。

短暂离线经过可配置宽限期再触发修复。后台任务限速，前台业务优先。NAS 恢复后核对对象版本，过期副本不能直接重新参与读取。

### 10.2 校验

版本保存可信校验信息，定期巡检。校验失败隔离副本，从健康副本修复。两份内容不同不能通过多数投票判断哪份正确，必须依赖可信校验或其他明确证据。

单次超时仅更新可用性观察，不删除副本位置。健康状态与副本持久身份分开管理。

### 10.3 回收

对象只有在不被当前版本、活跃读者、写入恢复任务、修复任务和保留策略引用时，才能进入回收流程。

回收使用精确对象 ID 和可恢复任务，考虑失效节点、在途 I/O 与恢复窗口。旧版本暂存主要服务安全回收，不自动等价于用户可恢复的历史版本功能。

## 11. 故障行为

| 故障 | 默认行为 |
| --- | --- |
| 接入节点退出 | 其他节点继续服务，客户端重连；未完成操作恢复或重试 |
| 元数据 leader 退出 | 多数派重新选主，操作短暂停顿 |
| 元数据失去多数派 | 停止变更和版本发布 |
| 双副本一个 NAS 离线 | 从另一副本读，标记降级并安排修复 |
| 双副本写入仅有一个可用故障域 | 默认拒绝提交，不静默降级 |
| 存在第三个可用 NAS | 可为新版本或修复选择新的双副本组合 |
| 所有副本不可用 | 保留命名空间，文件访问返回错误 |
| 旧节点仍能访问 NAS | 只能继续影响自己的未发布对象，不能发布过期版本 |
| 提交回复丢失 | 使用请求 ID 查询或重试，避免重复执行 |

副本提供设备故障容错，不替代备份。用户删除作用于逻辑文件，历史保留、误删除恢复和灾难恢复策略另行定义。Raft 副本也不等于离线备份。

## 12. 可观测性

管理界面至少展示：

- 节点、元数据组和 NAS 后端状态。
- 物理可用空间与当前策略下估算的逻辑可用空间。
- 空间预留、工作版本、待回收数据占用。
- 单副本、双副本达标、降级、不可用文件数量。
- 导入进度、冲突、等待副本和失败原因。
- 修复进度、待修复字节数、校验错误和任务重试状态。

凭证由节点配置或合适的凭证存储提供，不写入普通日志和文件元数据记录。跨节点身份映射与后端访问权限在部署设计中明确。

## 13. 实施与验证里程碑

### M0：Zig 与元数据核心

- 将当前 Rust 骨架转换为 Zig 项目并固定兼容依赖。
- 实现三节点目录操作、事务提交与请求去重。
- 验证重命名原子性、进程重启、日志与快照恢复。
- 文档编写不包含上述代码转换，需在后续实施任务执行。

### M1：多节点 SMB 原型

- 两个 SMB 接入节点，验证共享模式、偏移写、flush、重命名与删除。
- 验证 Windows Explorer、macOS Finder 及常见文档保存工作流。
- 验证跨节点缓存、写入冲突与节点隔离。
- 确定 FUSE、Samba VFS 与集群协调的最终组合。

### M2：多 NAS、双副本与导入

- 三个元数据节点、两个接入节点和至少两个 NAS 后端。
- 双副本严格提交、单副本策略和不同容量放置。
- 原地导入、冲突处理、等待副本和中断恢复。
- 副本修复与校验；替换故障域的验证需第三个 NAS 或等效独立测试后端。

### 13.1 关键验收用例

| 场景 | 验收要求 |
| --- | --- |
| A 创建后 B 查询 | 创建成功后的权威查询能看到文件 |
| 两节点同名创建 | 只有一个成功，无重复目录项 |
| 同文件并发写 | 不并行修改同一个工作对象 |
| 临时文件替换目标 | 目标引用原子切换 |
| flush 成功后接入进程崩溃 | 已确认版本仍可读取 |
| 双副本提交后一个 NAS 离线 | 文件仍可读取 |
| 第二份写入失败 | 不发布不满足策略的新版本 |
| 第一份完成后崩溃 | 根据任务记录恢复或安全清理 |
| 旧写入者网络隔离 | 无法提交过期版本 |
| 修复期间文件更新或删除 | 不挂错版本、不复活已删除文件 |
| 导入原路径被复用 | 不误接管或删除新文件 |
| 回收与读取并发 | 活跃读取所需对象不被提前删除 |
| 1 副本升级为 2 | 复制完成后才显示达标 |
| 2 副本降为 1 | 提交保留位置后安全回收 |

性能验证至少包括顺序吞吐、大文件多次 flush、修改旧文件的复制放大、双副本网络流量、目录枚举延迟和后台修复对前台的影响。

- 业务失败返回结果而不终止 Raft；损坏的已提交命令或内存分配失败保持逻辑状态不变。

验证覆盖确定性重放、重命名冲突和循环、非空目录删除、请求重试、快照内存所有权及分配失败。运行入口：

```sh
zig build
zig build test
zig build run -- metadata-demo
```

已接入 LMDB 0.9.36，本地元数据、请求结果与 applied index/term 在同一默认同步事务中落盘。现已完成三节点 Raft 网络运行与恢复（见第 17 节）；尚未写入 NAS，副本字段仍表示期望策略。

每个元数据节点使用本地 SSD 上的独立 LMDB 环境，不允许将数据库放在 SMB 共享上。`meta`、`inodes`、`dirents`、`requests` 四个 named database 分别保存游标与 ID 分配、inode、目录索引及去重结果。普通操作直接访问索引，不重写整份状态。读事务保持短生命周期，返回名称复制到调用方内存。

逻辑快照沿用版本 1 格式；当前有界原型在一个写事务内替换记录、重建目录索引和保存游标，失败全部回滚。恢复需要预留 copy-on-write 空间；未来大规模快照可采用独立环境构建与可恢复切换协议。map 满不自动扩容，存储错误映射为 Raft 终止错误，不能继续确认提交。默认不开启任何弱化同步持久性的 LMDB 标志。

新增 `metadata-apply DIRECTORY INDEX TERM JSON` 和 `metadata-show DIRECTORY` 本地调试入口，目录需预先建立，CLI map 大小为 256 MiB。它们直接操作独立测试数据库，不替代 Raft 提案。测试覆盖内存实现对照、重新打开后的去重和游标、快照恢复、map 满与分配失败回滚；断电验证尚待后续实施。

## 17. 三节点运行与恢复

CLI 已改用 zli v6.0.0，固定源码版本 `52a3773e7b825e755c878b022cb4f9c589c3712f`，提供帮助、参数解析及非零错误退出码。`serve` 启动固定三个 voter 的 Raft 组；`status` 查询本地角色、任期、leader ID、commit/applied index；`apply` 向 leader 提交元数据 JSON；`get` 经 ReadIndex 屏障读取 inode。

运行示例及完整参数见 `README.md` 的 Three-node development cluster。关键约定：

- 所有节点使用同一个非零 32 位十六进制 cluster ID、相同的三个 peer 配置，以及各自独立的 node ID 和数据目录；IPv4 API 与 Raft 使用不同监听端口。
- 每个节点的 `DATA_DIR/raft/` 保存 WAL、成员关系和快照，`DATA_DIR/metadata/` 保存 LMDB。LMDB 持久绑定 cluster/node identity；身份不一致拒绝启动，进程独占锁阻止同目录并发运行。本地修改命令拒绝写入集群数据库。
- raftz 使用 pre-vote、check-quorum，禁止 proposal forwarding；非 leader 拒绝写入与业务读取。`status` 仅为本地诊断，不能用于线性一致读取。
- API 在写入 Raft 前拒绝损坏 JSON、超长请求、版本不支持及零 request ID。RPC 使用 `proto/metadata.proto` 中的 Envelope 携带原型 JSON；命名空间业务失败仍作为结果返回。
- 写入成功代表多数派 WAL 提交且 leader 的 LMDB 已同步应用。请求超时不代表一定没提交；调用方需使用同一 request ID 和内容重试。多地址 CLI 探测与重试见第 18 节。
- 重启核对 LMDB applied cursor 与 WAL 的 commit/term；必要时恢复快照并重放未应用的已提交日志。落后节点在日志已压缩时通过网络快照追赶。自动快照默认阈值为 1000，测试使用 8。
- SIGINT/SIGTERM 停止接收 API 并清理运行线程；进程被 SIGKILL 后使用原目录和身份重启。LMDB 不能独立替代 Raft WAL 作为集群备份。

`zig build test-cluster` 启动三个真实进程，验证选主、请求去重、非 leader 拒绝、ReadIndex、leader 退出后选主与写入、网络快照追赶、全体 SIGKILL 后恢复、保留 WAL/快照重建缺失 LMDB，以及少数派不可确认写入与读取。集成测试使用临时目录和动态 loopback 端口，不修改现有集群。依赖 Linux io_uring。

当前仍为受信任开发网络上的明文原型。尚未实现动态成员管理、客户端身份域、TLS/认证、SMB/FUSE、NAS 物理副本、跨机器长时间负载及硬件断电测试。

## 18. 目录查询与客户端故障切换

新增 `lookup ENDPOINTS PARENT NAME` 和 `list ENDPOINTS PARENT --limit N --after NAME`，对应 Lookup/List RPC。二者先经过 ReadIndex，再在单个 LMDB 只读事务内校验父目录、查询目录索引及 inode，返回独立持有的名称。名称查找保持 ASCII 大小写不敏感；父目录不存在或不是目录返回明确错误。

目录按大小写折叠后的 UTF-8 字节序分页，每页最多 16 项。`next` 为本页最后名称，仅在还有后续项时返回；下一页从严格大于该名称的位置开始。游标项被删除后仍可继续。空目录返回空数组及 null 游标。每页独立一致，不跨页持有快照；并发插入、删除、重命名可能遗漏或重复条目，不能把多页遍历当作同一时刻的快照。

响应 Envelope 上限增至 32 KiB，覆盖 16 个最长名称的 JSON 转义及游标；请求和 Raft 命令仍限制为 4 KiB。测试覆盖大小写查询、分页顺序、已删除游标、结果所有权、空目录、非法参数及最大转义页面。

apply/get/lookup/list 接受同一集群最多三个逗号分隔的 API 地址，多地址调用最多探测五轮，每轮间隔一秒，单次 RPC 截止时间八秒。连接建立还受传输层及操作系统超时影响，因此这是尝试次数限制，不是整体耗时保证。连接失败、不可用、超时、背压和 leader 变化触发重试，其他错误立即返回；写入始终复用完全相同的 JSON 和 request ID。单地址不重试，status 保持单节点诊断。重试耗尽仍可能存在未知提交结果。

三进程集成测试新增 follower 优先的 leader 探测、leader 被杀后的自动写入重试、重启后完整分页遍历及错误分类验证。此层为后续 FUSE 提供目录查询能力，尚未定义 FUSE 的目录句柄及跨页缓存语义。

原型暂限 4096 个存活 inode、8192 条请求记录及 8 MiB 快照；请求记录不自动淘汰，达到上限后新请求被拒绝，已有请求仍可查询原结果。名称暂采用 ASCII 大小写不敏感比较与 UTF-8 校验，尚不构成完整 SMB 名称兼容。后续需要持久化存储、去重保留协议和客户端身份域。
