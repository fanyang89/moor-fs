# nas-fs 分布式文件服务设计

状态：已实现可运行原型，仍有生产化与多机验收边界。本文记录产品约定和历次实现；当前实现为第 38 节的后端双 staging 写会话。第 39 节记录已确认、尚未实现的 WAL 原地更新方向，取代目标设计中的不可变版本与旧读句柄保证。

## 1. 目标与范围

将局域网内容量不同的 NAS 通过 SMB 纳入统一存储池，由多个接入节点提供一致的 SMB 共享目录。

已确认的需求：

- 每个接入节点都能提供文件访问服务，客户端无需安装专用客户端。
- 支持 Windows、macOS 和 Linux 客户端挂载 SMB 共享。
- 面向照片、视频、文档和备份，支持普通文件所需的偏移写、截断和 flush，但不针对数据库、虚拟机磁盘等高频随机写负载优化。
- 文件完整存放在 NAS 上，首版不跨 NAS 分块。
- 默认双副本，支持单副本；双副本必须位于不同物理 NAS。
- 用户可以在 NAS 管理界面将已有文件或目录移动到导入区；系统发现并接管，路径冲突需要明确提示。
- 实现语言采用 Zig，核心依赖自有 grpc-lite 和 raftz。

首版范围之外：多元数据分片、透明 SMB 会话故障接管、重度随机写优化、自动跨地域复制。

## 2. 整体架构

```text
                 局域网 SMB 客户端
                  /      |      \
               节点 A   节点 B   节点 C
               Samba    Samba    Samba
                  |       |       |
                文件系统适配与 nas-fs 服务
                  |               |
                  +-- 元数据组 ---+
                  | raftz，3 副本 |
                  | 本地 LMDB     |
                  |               |
                  +-- SMB 后端访问 --+
                         |          |
                       NAS A      NAS B ...
```

### 2.1 节点角色

- **接入节点**：处理 SMB 文件操作、访问后端、执行导入与恢复任务。
- **元数据节点**：保存权威命名空间、版本、副本位置、写入协调和任务状态。
- **NAS 后端**：通过 SMB 提供文件存储，无需运行 nas-fs 程序。

首版使用一个 Raft 组、三个投票成员，可与接入节点共机部署。增加接入节点不必增加投票成员。元数据 leader 负责协调提交，不中转文件数据。

默认所有接入节点都能访问所有 NAS，避免单个接入节点故障导致某台 NAS 失去入口。

### 2.2 客户端入口

每个节点提供相同共享，例如 `\\node-a\pool`、`\\node-b\pool`。

首版使用明确节点地址。统一域名和接入调度可后续增加；DNS 切换不等于已有 SMB 会话或打开句柄的透明接管。节点故障后，受影响客户端需要重连或重试。

## 3. 技术栈与复用边界

| 组件 | 规划职责 |
| --- | --- |
| Zig | 核心服务实现 |
| grpc-lite | 内部 RPC 与 raftz 的传输能力 |
| raftz | 元数据共识、日志复制与状态机编排 |
| LMDB | 本地已应用元数据状态，默认同步事务 |
| Samba | SMB 协议、认证与客户端会话 |
| Linux CIFS | 优先作为 NAS SMB 访问方式 |
| FUSE / Samba VFS | 通过原型决定具体组合 |

### 3.1 本地代码检查结论

检查时的 zookeeper-zig 使用 Zig 0.17.0，服务端采用 raftz、grpc-lite 和 RocksDB。其设计将业务变更与 Raft applied index、term 在 RocksDB 同步写批次中原子提交。

`zookeeper-zig/src/server/quorum.zig` 的 `Quorum` 直接持有 `ZooKeeperStateMachine`，不是可直接替换状态机的通用宿主。raftz 已提供独立的 `StateMachine` 接口与 `Raftor` 编排层。

因此，nas-fs 直接实现 raftz 状态机，不依赖或部署 zookeeper-zig，也不将文件映射成 znode。zookeeper-zig 仅作为设计时参考的已有实现，不加入项目依赖或 submodule。

grpc-lite 不自动重放 RPC，nas-fs 必须实现请求标识、结果查询、去重与安全重试。

工具链与依赖版本在实施时重新核对并固定。沿用各依赖的标准获取与校验流程，不修改共享依赖缓存。

## 4. 命名空间与存储布局

客户端看到统一逻辑目录，不暴露文件所在 NAS。目录项通过稳定文件 ID 引用文件，后端对象名不随逻辑路径变化。

每个后端建立专用目录：

```text
nas-fs/
├── import/       用户放入待导入文件
├── staging/      未发布写入、导入接管和恢复数据
└── objects/      已发布对象
```

`objects/` 和 `staging/` 应限制普通用户直接修改。用户通过 NAS 管理界面操作 `import/`，文件接管后通过统一共享管理。

- 逻辑重命名和目录移动只更新元数据，不迁移文件内容。
- 已发布对象不可修改；新内容生成新版本。
- 单个文件必须能完整容纳于每个目标 NAS，存储池总剩余空间不代表单文件可写空间。
- 全部节点使用一致的名称比较规则，同时保留原始显示名称。大小写、Unicode、保留名称及 SMB 名称约束需要在原型中明确。

## 5. 元数据模型与一致性

### 5.1 逻辑记录

| 记录 | 主要内容 |
| --- | --- |
| inodes | 稳定文件 ID、类型、属性、当前版本、期望副本数 |
| dirents | 父目录 ID、规范化名称、显示名称、文件 ID |
| versions | 版本 ID、大小、校验信息与副本列表 |
| replicas | 后端 ID、对象 ID、验证状态 |
| backends | NAS 标识、共享位置、故障域和管理状态 |
| write_sessions | 持有者、写入代次、预期旧版本、工作对象 |
| reservations | 各后端空间预留 |
| operations | 导入、发布、删除、修复等任务状态 |
| requests | 请求 ID、提交结果与去重保留信息 |

具体编码、索引与键布局在实施阶段确定。

### 5.2 提交原则

- 命名空间、版本发布、策略变更与相关任务记录使用同一个元数据事务域。
- 状态机只执行确定性操作，不在 apply 中读取实际时间、扫描 NAS 或执行网络 I/O。
- 业务变更和 applied index、term 原子持久化。
- 权威读取通过线性一致读屏障和本地应用进度检查实现；缓存必须有明确失效规则。
- 超时可能表示结果未知，客户端通过请求 ID 查询或重试，不直接认定事务失败。
- 去重记录设置保留范围，客户端重试必须遵守相应期限。

Raft 多数派不可用时停止元数据变更。已固定版本的读取是否继续，需要同时满足对象引用、句柄与租约有效性，不能无条件放行。

## 6. 副本策略

### 6.1 策略继承

存储池默认两副本；目录可覆盖为一副本或两副本。文件创建或导入时记录有效策略。

- 修改文件内容沿用其已有策略。
- 重命名和移动不自动改变策略。
- 调整目录策略时，可明确选择是否应用到已有文件，由后台任务执行。
- 一副本升为两副本后，在复制完成前显示未达标。
- 两副本降为一副本时，先事务提交保留位置及新策略，再安全回收多余副本。

元数据 Raft 三副本与文件副本数相互独立。

### 6.2 故障域与放置

每个后端配置 `failure_domain`，对应实际物理 NAS。同一 NAS 的多个共享不能充当独立副本。

双副本放置必须选择两个不同故障域，并分别满足空间要求。默认按有效剩余容量及负载选择，允许目录级放置约束。

```text
有效可用空间 = NAS 报告可用空间 - 安全余量 - 尚未完成写入的空间预留
```

空间预留通过元数据事务协调。外部导入、其他 NAS 用户和未知长度写入仍可能消耗额外空间，必须处理真实的空间不足错误。

双副本可用容量不简单等于总空间的一半。例如仅有剩余 4 TB 和 12 TB 的两台 NAS，双副本逻辑增量容量至多约为 4 TB，还需扣除安全余量、工作版本等开销。

### 6.3 严格提交

默认不静默降级。双副本版本只有在两份内容均准备完成、通过一致性校验且完成后端 flush 后，才提交元数据并确认成功。

发布对象、版本映射与客户端确认之间仍存在跨系统事务边界，必须通过持久化操作记录恢复。持久性最终依赖 NAS 正确实现 SMB flush 及其底层存储保证。

写入一份失败时不发布新版本，旧版本继续作为已提交状态。若结果未知，先查询发布事务结果，避免误清理已经提交的对象。

## 7. 文件写入与版本发布

### 7.1 写入流程

```text
分配写入代次、工作对象和空间预留
    → 向各目标副本执行相同的有序偏移写入
    → 完成校验与后端 flush
    → 将对象封存为不可变候选版本
    → 校验写入代次和预期旧版本
    → Raft 提交版本与副本位置
    → 返回提交成功
```

随机偏移写和截断必须纳入最终内容校验，不能将到达顺序的输入字节哈希直接视为最终文件哈希。首版可在封存阶段扫描校验，分段校验与优化方式待验证。

写租约本身不能阻止失联节点继续访问普通 NAS。因此工作对象按写入尝试隔离，已发布对象不可修改；过期节点不能通过代次检查发布自己的对象。

删除、垃圾回收和恢复操作也必须针对精确对象身份执行，不能凭租约超时就删除来源不明的路径。

### 7.2 FLUSH 与后续写入

SMB 句柄可能反复写入、flush、继续写入。成功返回的 flush 必须形成符合副本策略、可恢复的持久化边界。

```text
工作版本 W1 → flush 并发布 V1
                    ↓ 下一次修改
                工作版本 W2 → flush 并发布 V2
```

已发布 V1 不再原地修改；没有后续变更时不创建 W2。修改已有大文件可能需要完整复制，每次发布后再修改也可能引入复制放大。

首版接受整文件版本化的简洁模型，但必须测量大文件多次 flush 和小修改的成本。若不满足普通文件工作流，再设计增量工作区或分块方案。

## 8. SMB 接入语义

### 8.1 基础约定

| 操作 | 首版语义 |
| --- | --- |
| 创建 | 原子创建目录项，同名竞争只有一个成功 |
| 读取 | 在有效协调状态下读取确定的已提交版本 |
| 写入 | 同一文件只允许一个有效写入者 |
| 偏移写、截断 | 支持，作用于工作对象 |
| flush | 满足副本策略并持久提交后返回成功 |
| 关闭写句柄 | 提交剩余变更并释放写入权；失败需反馈或记录 |
| 重命名 | 原子更新命名空间，检查共享访问规则 |
| 替换 | 原子切换目标引用，不暴露部分新内容 |
| 删除 | 逻辑删除与物理回收分离，尊重打开句柄规则 |
| 目录枚举 | 支持分页，并发修改下不承诺整次枚举固定快照 |

首版候选为“多读或单写”的保守模型：已有读者可能阻止写打开，已有写者可能阻止其他读写打开。该限制必须通过常见应用验证；如影响正常保存，则扩展共享访问模型。

### 8.2 协调状态

区分 SMB 会话、打开句柄和写入事务。使用稳定文件 ID 协调，不以路径充当锁身份。租约失效后停止依赖该租约的访问，正在处理的操作也需要有效性检查。

多台 Samba 挂载同一逻辑 FUSE 文件系统，并不会自动具备跨节点共享模式、字节范围锁、删除意图、oplock 和 lease 一致性。

原型需要决定：

- Samba 集群机制与 FUSE 是否能传递并协调所需状态。
- 是否增加 Samba VFS 集成。
- Samba 打开句柄协调与 nas-fs 版本发布代次的职责如何衔接。
- 如何统一用户身份、权限和客户端缓存失效。

不能正确跨节点协调的客户端缓存能力首版关闭。完整 ACL、扩展属性、备用数据流等兼容性另行确认，不预先承诺。

## 9. NAS 原地导入

### 9.1 用户操作

用户将已有目录移动到某 NAS 的 `nas-fs/import/`，相对路径映射到统一共享。

例如 `NAS B:/nas-fs/import/photos/2026/` 导入为 `\\node-a\pool\photos\2026\`。

原文件保留在 NAS B 作为第一份数据。若源与接管目录在支持重命名的同一文件系统内，可避免复制第一份内容；跨卷移动不保证零复制。

### 9.2 发现与接管

使用 SMB 通知降低发现延迟，定期扫描兜底。按后端协调扫描任务，持久化任务记录以避免重复导入。

```text
DISCOVERED → CLAIMED → STAGED → REPLICATING → PUBLISHED
                  ↘ CONFLICT / FAILED / WAITING
```

- 自动导入依据稳定窗口尝试接管，但大小和修改时间稳定并不能证明复制已完成。
- 支持用户确认“已放置完成”后启动导入，适用于复制中的大目录。
- 接管期间要求用户停止修改文件；NAS 本地操作可能绕过 SMB 共享模式限制。
- 检测到变化则暂停或失败，不发布不确定内容。
- 任务记录源路径、目标路径、对象 ID及可获得的文件身份信息，恢复时核对实际状态。
- 原路径被新文件复用且无法可靠区分时，进入待确认状态，不猜测身份。

### 9.3 副本与可见性

默认双副本：接管第一份后复制到另一 NAS，校验并 flush，最后提交元数据。

第二份暂时无法完成时显示“等待副本”，保留已接管文件，不宣称导入完成。用户可以明确改为单副本后完成导入。

目录批量导入逐文件提交并显示进度，不承诺整棵目录原子出现。

### 9.4 冲突

- 同名目录合并处理子项。
- 同路径文件、文件与目录重名、大小写等名称冲突不自动覆盖。
- 用户可选择跳过、重命名后导入或明确确认替换。
- 最终提交仍需事务检查路径冲突，不能仅依赖扫描时检查。
- 失败、冲突和等待状态的文件不自动删除。

## 10. 修复、巡检与回收

### 10.1 副本修复

```text
发现副本不足 → 分配任务与空间 → 固定健康源版本
    → 复制到新故障域 → 校验并 flush → 条件提交副本位置
```

提交时重新核对文件版本、策略和任务代次，防止旧版本副本被挂到新版本上。复制期间持有源对象引用，避免被提前回收。

短暂离线经过可配置宽限期再触发修复。后台任务限速，前台业务优先。NAS 恢复后核对对象版本，过期副本不能直接重新参与读取。

### 10.2 校验

版本保存可信校验信息，定期巡检。校验失败隔离副本，从健康副本修复。两份内容不同不能通过多数投票判断哪份正确，必须依赖可信校验或其他明确证据。

单次超时仅更新可用性观察，不删除副本位置。健康状态与副本持久身份分开管理。

### 10.3 回收

对象只有在不被当前版本、活跃读者、写入恢复任务、修复任务和保留策略引用时，才能进入回收流程。

回收使用精确对象 ID 和可恢复任务，考虑失效节点、在途 I/O 与恢复窗口。旧版本暂存主要服务安全回收，不自动等价于用户可恢复的历史版本功能。

## 11. 故障行为

| 故障 | 默认行为 |
| --- | --- |
| 接入节点退出 | 其他节点继续服务，客户端重连；未完成操作恢复或重试 |
| 元数据 leader 退出 | 多数派重新选主，操作短暂停顿 |
| 元数据失去多数派 | 停止变更和版本发布 |
| 双副本一个 NAS 离线 | 从另一副本读，标记降级并安排修复 |
| 双副本写入仅有一个可用故障域 | 默认拒绝提交，不静默降级 |
| 存在第三个可用 NAS | 可为新版本或修复选择新的双副本组合 |
| 所有副本不可用 | 保留命名空间，文件访问返回错误 |
| 旧节点仍能访问 NAS | 只能继续影响自己的未发布对象，不能发布过期版本 |
| 提交回复丢失 | 使用请求 ID 查询或重试，避免重复执行 |

副本提供设备故障容错，不替代备份。用户删除作用于逻辑文件，历史保留、误删除恢复和灾难恢复策略另行定义。Raft 副本也不等于离线备份。

## 12. 可观测性

管理界面至少展示：

- 节点、元数据组和 NAS 后端状态。
- 物理可用空间与当前策略下估算的逻辑可用空间。
- 空间预留、工作版本、待回收数据占用。
- 单副本、双副本达标、降级、不可用文件数量。
- 导入进度、冲突、等待副本和失败原因。
- 修复进度、待修复字节数、校验错误和任务重试状态。

凭证由节点配置或合适的凭证存储提供，不写入普通日志和文件元数据记录。跨节点身份映射与后端访问权限在部署设计中明确。

## 13. 实施与验证里程碑

### M0：Zig 与元数据核心

- 将当前 Rust 骨架转换为 Zig 项目并固定兼容依赖。
- 实现三节点目录操作、事务提交与请求去重。
- 验证重命名原子性、进程重启、日志与快照恢复。
- 文档编写不包含上述代码转换，需在后续实施任务执行。

### M1：多节点 SMB 原型

- 两个 SMB 接入节点，验证共享模式、偏移写、flush、重命名与删除。
- 验证 Windows Explorer、macOS Finder 及常见文档保存工作流。
- 验证跨节点缓存、写入冲突与节点隔离。
- 确定 FUSE、Samba VFS 与集群协调的最终组合。

### M2：多 NAS、双副本与导入

- 三个元数据节点、两个接入节点和至少两个 NAS 后端。

## 17. 三节点运行与恢复

CLI 已改用 zli v6.0.0，固定源码版本 `52a3773e7b825e755c878b022cb4f9c589c3712f`，提供帮助、参数解析及非零错误退出码。`serve` 启动固定三个 voter 的 Raft 组；`status` 查询本地角色、任期、leader ID、commit/applied index；`apply` 向 leader 提交元数据 JSON；`get` 经 ReadIndex 屏障读取 inode。

运行示例及完整参数见 `README.md` 的 Three-node development cluster。关键约定：

- 所有节点使用同一个非零 32 位十六进制 cluster ID、相同的三个 peer 配置，以及各自独立的 node ID 和数据目录；IPv4 API 与 Raft 使用不同监听端口。
- 每个节点的 `DATA_DIR/raft/` 保存 WAL、成员关系和快照，`DATA_DIR/metadata/` 保存 LMDB。LMDB 持久绑定 cluster/node identity；身份不一致拒绝启动，进程独占锁阻止同目录并发运行。本地修改命令拒绝写入集群数据库。
- raftz 使用 pre-vote、check-quorum，禁止 proposal forwarding；非 leader 拒绝写入与业务读取。`status` 仅为本地诊断，不能用于线性一致读取。
- API 在写入 Raft 前拒绝损坏 JSON、超长请求、版本不支持及零 request ID。RPC 使用 `proto/metadata.proto` 中的 Envelope 携带原型 JSON；命名空间业务失败仍作为结果返回。
- 写入成功代表多数派 WAL 提交且 leader 的 LMDB 已同步应用。请求超时不代表一定没提交；调用方需使用同一 request ID 和内容重试。多地址 CLI 探测与重试见第 18 节。
- 重启核对 LMDB applied cursor 与 WAL 的 commit/term；必要时恢复快照并重放未应用的已提交日志。落后节点在日志已压缩时通过网络快照追赶。自动快照默认阈值为 1000，测试使用 8。
- SIGINT/SIGTERM 停止接收 API 并清理运行线程；进程被 SIGKILL 后使用原目录和身份重启。LMDB 不能独立替代 Raft WAL 作为集群备份。

`zig build test-cluster` 启动三个真实进程，验证选主、请求去重、非 leader 拒绝、ReadIndex、leader 退出后选主与写入、网络快照追赶、全体 SIGKILL 后恢复、保留 WAL/快照重建缺失 LMDB，以及少数派不可确认写入与读取。集成测试使用临时目录和动态 loopback 端口，不修改现有集群。依赖 Linux io_uring。

当前仍为受信任开发网络上的明文原型。尚未实现动态成员管理、客户端身份域、TLS/认证、SMB/FUSE、NAS 物理副本、跨机器长时间负载及硬件断电测试。

## 18. 目录查询与客户端故障切换

新增 `lookup ENDPOINTS PARENT NAME` 和 `list ENDPOINTS PARENT --limit N --after NAME`，对应 Lookup/List RPC。二者先经过 ReadIndex，再在单个 LMDB 只读事务内校验父目录、查询目录索引及 inode，返回独立持有的名称。名称查找保持 ASCII 大小写不敏感；父目录不存在或不是目录返回明确错误。

目录按大小写折叠后的 UTF-8 字节序分页，每页最多 16 项。`next` 为本页最后名称，仅在还有后续项时返回；下一页从严格大于该名称的位置开始。游标项被删除后仍可继续。空目录返回空数组及 null 游标。每页独立一致，不跨页持有快照；并发插入、删除、重命名可能遗漏或重复条目，不能把多页遍历当作同一时刻的快照。

响应 Envelope 上限增至 32 KiB，覆盖 16 个最长名称的 JSON 转义及游标；请求和 Raft 命令仍限制为 4 KiB。测试覆盖大小写查询、分页顺序、已删除游标、结果所有权、空目录、非法参数及最大转义页面。

apply/get/lookup/list 接受同一集群最多三个逗号分隔的 API 地址，多地址调用最多探测五轮，每轮间隔一秒，单次 RPC 截止时间八秒。连接建立还受传输层及操作系统超时影响，因此这是尝试次数限制，不是整体耗时保证。连接失败、不可用、超时、背压和 leader 变化触发重试，其他错误立即返回；写入始终复用完全相同的 JSON 和 request ID。单地址不重试，status 保持单节点诊断。重试耗尽仍可能存在未知提交结果。

三进程集成测试新增 follower 优先的 leader 探测、leader 被杀后的自动写入重试、重启后完整分页遍历及错误分类验证。此层为后续 FUSE 提供目录查询能力，尚未定义 FUSE 的目录句柄及跨页缓存语义。

## 19. 只读 FUSE 命名空间原型

通过 `python3 tools/deps.py build-fuse` 构建固定版本 libfuse，再执行 `zig build -Dfuse=true` 启用 `mount ENDPOINTS MOUNTPOINT`。默认构建无需 libfuse。mount 在前台运行，使用系统 `/dev/fuse` 和 fusermount3；SIGINT/SIGTERM 或正常卸载会释放会话与目录句柄。

采用 libfuse low-level API：小型 C 桥处理 Linux stat、目录编码及会话生命周期，Zig 层调用现有元数据 RPC，复用多地址 leader 探测与重试。lookup/getattr 的 entry/attribute timeout 均为零；命名空间更新通过后续远端读取可见，不缓存负查询。稳定 inode ID 直接映射 FUSE inode。

opendir 读取所有目录页并添加 `.`/`..`，为该句柄保存独立条目数组；readdir 用数组下标作下一项偏移，后续重命名不改变已打开句柄的条目与偏移。重新打开目录刷新视图。收集期间仍遵循各页独立一致的语义，不构成全局快照；检测到重复 inode 或超过容量时返回 EAGAIN，但不能检测所有遗漏。每个挂载最多保留 64 个目录句柄，每个句柄受 4096 inode 上限约束，releasedir 与会话销毁均清理资源。

本阶段挂载仅提供只读命名空间；后续第 23 节已接入版本大小与对象读取。目录权限 0555、普通文件 0444，UID/GID 使用挂载用户身份，挂载层拒绝写入。权限模型及 Samba 尚未接入。

`zig build test-fuse -Dfuse=true` 运行三节点恢复测试并创建两个真实挂载点，验证目录与 inode、大小写名称、分页遍历、打开目录期间重命名的偏移稳定性、跨挂载更新、只读错误、文件内容不支持、leader 退出后的查询以及清理卸载。当前单线程 FUSE 循环会被远端慢请求阻塞，后续数据层和 SMB 验证需继续处理并发、取消和缓存一致性。

原型暂限 4096 个存活 inode、8192 条请求记录及 8 MiB 快照；请求记录不自动淘汰，达到上限后新请求被拒绝，已有请求仍可查询原结果。名称暂采用 ASCII 大小写不敏感比较与 UTF-8 校验，尚不构成完整 SMB 名称兼容。后续需要去重保留协议和客户端身份域。

## 20. 后端登记与不可变版本发布

新增 `register_backend` 命令登记非零数值后端 ID 与物理故障域 ID。登记不可覆盖；同一物理 NAS 的多个共享必须登记相同故障域。当前最多 64 个后端，仅记录身份和故障域，挂载地址、凭证与健康状态尚未接入。

文件 inode 新增 `current_version`，零表示尚未发布。`publish` 接收 `expected_version` 与不可变版本记录：全局非零版本 ID、inode、大小、32 字节 SHA-256、两个后端槽位。大小不超过 i64 最大值；JSON 校验和固定输出数值数组，避免字节恰好构成 UTF-8 时变成字符串。单副本用 `[backend,0]`，双副本必须使用不同物理故障域的已登记后端。

发布以 `expected_version == current_version` 作 CAS，副本数必须符合文件当前策略。版本 ID 不可复用。并发发布同一旧版本最多一个成功，另一个返回 `version_conflict`；其他校验错误包括 `not_file`、`invalid_version`、`replica_mismatch`、`backend_not_found` 和 `same_failure_domain`。重试复用请求 ID 和内容；失败结果同样保留去重记录。

LMDB 在同一同步事务中提交版本、当前指针、请求回执和 applied 游标。重命名不改变版本；替换和删除 inode 均保留历史版本。策略变化不追溯修改旧版本，也不触发真实复制。当前最多保留 2048 个版本，达到上限拒绝新版本，尚无垃圾回收。

CLI `backend ENDPOINTS ID`、`file-version ENDPOINTS ID` 分别查询后端与版本，经 ReadIndex 保护；不存在返回 null。`get` 返回当前版本 ID。请求 JSON 示例见 README。

数据库打开时以事务将 schema 1 升级至 2，增加 backends/versions 数据库。新快照版本为 2，恢复兼容版本 1；旧 inode 缺省当前版本为零，旧快照缺省后端和版本列表为空。既有命名空间请求的摘要保持不变。升级需统一节点版本，不支持混合版本运行或降级。

本轮仅验证元数据中的副本声明，不读取 NAS、不计算实际文件校验和、不执行复制或 flush，也未实现写会话 fencing。因此 publish 成功不能作为文件已在双 NAS 持久化的证明；数据层完成这些步骤后才能满足前文严格双副本确认协议。FUSE 文件读取仍未开放。

验证覆盖内存/LMDB 状态一致性、CAS 竞争、故障域与策略校验、历史保留、旧库及旧快照兼容、分配失败和 map-full 回滚，以及三进程故障切换、快照/WAL 重建和双 FUSE 挂载回归。

## 21. 已挂载目录的整文件对象通路

新增 `put-file ENDPOINTS CONFIG JSON SOURCE` 与 `get-file ENDPOINTS CONFIG INODE DESTINATION`。CONFIG 是本地 JSON 数组，条目为 `{"id":1,"root":"/mnt/nas-a/nas-fs"}`；后端 ID 必须已登记，root 是预先存在的绝对路径，挂载地址与凭证不进入 Raft。put 的 JSON 包含 `request_id`、`inode`、`version_id`、`expected_version`、`backends`，例子见 README。目录映射由管理员维护，不能把同一物理 NAS 误登记成不同故障域。

写入顺序：
1. 对源文件分块计算大小和 SHA-256，查询当前 inode、版本 ID 与后端，预检 CAS、副本策略和故障域。
2. 在各后端初始化 import/staging/objects 目录。以随机独占名称写入 staging，使用 256 KiB 固定缓冲区，校验复制内容与初始摘要一致。
3. 同步文件并读回校验，通过原子不覆盖重命名安装为 `objects/<十进制版本ID>-<小写SHA256>`。文件名包含摘要，防止并发误用相同版本 ID 的不同内容相互覆盖。
4. 同步 objects 与 staging 目录。若目标已存在，必须校验并同步已有对象，不能截断或覆盖。所有指定副本完成后才提交元数据 publish CAS，任何副本失败均不降级发布。

重试保持原始 JSON 和源文件内容不变。已发布的同版本同内容请求直接重放元数据请求，不代表修复副本。元数据响应遵循 apply 的 JSON 状态约定，调用者必须检查 status；本地预检/I/O 错误以非零退出。CAS 失败、RPC 结果不确定或进程崩溃都可能留下未引用对象，不能在错误处理里删除已安装对象。正常错误清理本次 staging，SIGKILL 可能留下临时文件；尚无 GC 或断点续传。

读取固定在线性一致 inode 查询中观察到的版本，按版本中后端顺序校验完整对象，缺失、不可读或摘要错误时尝试下一副本。目标路径必须不存在；在同目录临时文件中完成复制与再次摘要校验、fsync 后不覆盖重命名。复制阶段再次遇到源错误则本次失败，重试重新选副本。读取期间发生版本替换不会转而读取新版本；历史对象当前仍保留。

本轮以本地真实目录验证多块数据、空文件、单/双副本、第二副本失败不发布、损坏与离线回退、符号链接拒绝、重试不覆盖、并发发布和整集群重启。新增对象单测覆盖源文件变更拒绝、重开校验和导出不覆盖。FUSE 文件句柄接入见第 23 节。

边界：管理员须确保 NAS 挂载仍在、不同 ID 映射正确且目录无非受控修改；当前只拒绝重复路径/ID 和规范化后相同的双副本根，不能验证真实物理身份。root 与对象拒绝符号链接，父路径仍属于可信配置。staging 与 objects 必须同文件系统，要求原子不覆盖 rename 和文件/目录 fsync，不支持则失败。真实 CIFS 通路验证见第 22 节，NAS 断电持久性尚未验证；读回可能命中客户端缓存，fsync 的硬件保证依赖服务端。上传要求源文件稳定，大小/时间戳和哈希检测不等于源快照。尚无写会话 fencing、空间预留、自动导入、修复、NAS I/O 截止时间；选举分票可能超过既有客户端有限重试窗口，需要稍后重试。

## 22. 真实 Samba/CIFS 后端 E2E

新增 `zig build test-e2e`，可附加 `-Doptimize=safe`。Linux 环境需安装 smbd、smbclient、mount.cifs、umount、unshare 和 Python 3，支持内核 CIFS、mount namespace 与免交互 `sudo -n`。由普通用户启动，特权 worker 只在私有挂载命名空间内管理 Samba 和 CIFS；元数据集群及对象操作降权到调用用户。

测试启动两个仅监听 loopback 随机高端口的 Samba 实例，配置、状态库和导出目录全部独立。CIFS 使用 SMB 3.1.1、显式 guest 用户和 `cache=none,actimeo=0`。不修改系统 Samba 配置，不占用标准 SMB 端口。Samba guest account 映射到调用用户；不再叠加 force user，避免权限令牌与目录所有者映射不一致。挂载后先验证普通用户可创建/删除目录。

复用三节点恢复与对象测试，覆盖双副本写入、第二副本失败不发布、重试不覆盖、损坏和路径不可用回退、空文件、单副本、并发 CAS、leader 切换及整集群重启。额外用独立 smbclient 下载两份已发布对象核对字节；在服务端目录注入符号链接，验证拒绝读取。最后卸载 CIFS、重启 Samba、重新挂载并核对所有对象名称中的 SHA-256。路径不可用通过重命名目录模拟，尚不覆盖 NAS 网络中断和阻塞 I/O 超时。

成功后终止进程组、卸载并删除工作目录；失败保留 `${TMPDIR:-/tmp/opencode}/nas-fs-e2e-*` 中的 Samba 日志和对象。已在 Samba 4.24.7 与 Linux CIFS 上验证。该测试覆盖后端 SMB 传输，并非尚未实现的统一命名空间 SMB 客户端入口；服务进程重启和重新挂载不等价于 NAS 硬件断电测试。

## 23. FUSE 只读文件句柄与版本固定

`mount ENDPOINTS MOUNTPOINT --backends backends.json` 复用对象 CLI 的本地后端映射与配置校验。未指定映射时保留命名空间模式，文件打开返回 EOPNOTSUPP。lookup/getattr 查询 inode 指向的不可变版本，报告真实大小；未发布文件显示大小零，但配置后端后的 open 返回 ENODATA，不能冒充已发布空文件。时间戳仍为零。

open 经线性一致查询获取 inode，并固定该次观察到的版本。按版本中的后端顺序打开对象，完整校验大小和 SHA-256，失败则尝试下一副本；无健康副本返回 EIO。成功后将对象描述符和固定大小交给 C 桥持有，read 用 pread 支持随机偏移、尾部短读及 EOF。新版本发布、元数据改名或删除不改变已打开句柄的内容；重新打开观察新版本。带有效文件句柄的 getattr 使用句柄属性，不带句柄的属性查询仍描述当前版本。

FUSE open 设置 direct_io，不复用 inode 级内核页缓存，避免同一 inode 的新旧版本串读。每次 read 缓冲区上限 1 MiB，读取错误或固定 EOF 之前意外截断返回 EIO。每个挂载最多 64 个文件/目录句柄；release、打开响应失败及卸载均关闭对象描述符或释放目录数组。

目前校验发生在 open，而非每次范围读取。对象需保持不可变：打开后同大小原地篡改不会逐段检测；读错误不在原句柄内自动重选副本，调用方可重新打开。单线程 FUSE 循环、整文件打开校验和无截止时间的 NAS I/O 仍限制延迟与并发；尚不提供 mmap、写入、SMB share-mode、完整文件时间戳或跨节点权限语义。

`zig build test-fuse -Dfuse=true` 覆盖双挂载读取、真实大小、多块与跨边界偏移、EOF、新旧句柄并存、损坏/路径不可用回退、已打开对象被截断时的错误、空文件、未发布文件、leader 切换及元数据删除后句柄继续读取。`zig build test-e2e -Dfuse=true -Doptimize=safe` 将同一套 FUSE 验证接到两个真实 Samba/CIFS 后端，再执行服务重启和重新挂载后的对象哈希检查。

## 24. 只读 SMB 接入节点原型

新增 `python3 tools/serve_smb.py MOUNTPOINT NEW_STATE_DIRECTORY --port 1445`，将已有 nas-fs FUSE 挂载导出为 `[nas]` SMB3 共享。脚本检查挂载类型、来源和所有者，以同一普通用户运行 Samba，无需 allow_other 或修改系统 Samba 服务。状态目录必须新建，隔离 private/state/cache/lock/pid/ncalrpc 与日志；启动前调用 testparm 校验配置。前台运行，SIGINT/SIGTERM 清理服务进程组，保留状态目录供诊断。

默认只监听 127.0.0.1，可用 `--listen 本机IPv4` 显式绑定 LAN 地址。当前采用单用户 guest 只读共享，全部客户端映射为挂载用户，SMB 上传、删除、改名及建目录被拒绝。尚无生产认证、账号隔离和完整 ACL；Windows/macOS 客户端尚未验证，测试采用指定端口和 guest 用户的 smbclient。

元数据通过 CLI/Raft 更新，Samba 本地锁数据库不会接收到跨节点发布通知。因此关闭 SMB2 leases、oplocks、level2/kernel oplocks，并关闭 sendfile，使用 FUSE 固定版本读取路径。测试只证明新连接/打开可见版本与命名空间更新，不承诺任意客户端缓存刷新或 change notify 事件。时间戳仍为零，打开仍需整文件哈希。CTDB、跨节点 SMB 锁、durable handle 迁移及写入协议尚未实现。

`zig build test-smb -Dfuse=true`（可附加 `-Doptimize=safe`）在私有 mount namespace 中串联完整链路：两个独立 Samba 接入节点 → 各自 FUSE 挂载 → 两份 CIFS 后端 → 两个后端 Samba 服务。验证目录和文件大小、精确下载、只读拒绝、同大小内容替换、改名/删除可见性、空文件、损坏副本回退、全部损坏报错和元数据 leader 切换；最后仍执行后端重启/重新挂载哈希检查。

集群测试同时按既有客户端契约处理选举窗口：leader 退出后的第一次重放若明确返回 ClusterUnavailable，等待新 leader 后原样重放并检查去重结果。其他错误仍失败，没有扩展运行时重试次数或无限重试。测试退出信号触发 Python 清理路径，先关闭接入 Samba，再卸载 FUSE 和后端 CIFS。

## 25. 当前版本副本健康检查

新增 `nas-fs check-file ENDPOINTS backends.json INODE`。通过线性一致 inode 查询固定当前版本，再逐一打开其声明的副本，完整校验大小与 SHA-256。与下载只选择一份健康副本不同，检查会遍历所有声明位置。输出 JSON 包含 inode、version、size、healthy_replicas、all_healthy 及逐后端 replicas，单副本版本只产生一项。

副本状态为 healthy、missing（成功打开对象库后找不到对象）、corrupt（大小或哈希不符）、unavailable（对象库不可访问、读取失败、对象不稳定或类型不合法）、unconfigured（本机缺少该后端映射）。失败项的 reason 保留底层错误名，健康项为 null。完整检查即使发现所有副本损坏也正常退出，调用方应读取 JSON；配置错误、元数据查询失败、目录或未发布文件则返回命令错误。

检查不修改元数据或对象内容，不初始化后端目录，也不自动修复。all_healthy 仅描述该版本声明的副本，不表示满足之后改变的期望副本策略。各副本按顺序检查，并非同一时刻的健康快照；扫描期间可能发布新版本，报告里的版本 ID 用于明确观察对象。整文件校验同步执行，尚无 NAS I/O 超时或后台扫描调度。

现有对象集群测试与真实 Samba/CIFS E2E 增加健康双副本、缺少映射、后端路径不可用、对象缺失、同大小内容损坏、两份均损坏、空文件、单副本和整集群重启后的检查，并核对检查未创建缺失路径或改写损坏对象及版本记录。

## 26. 已声明位置的缺失副本补齐

新增 `nas-fs repair-file ENDPOINTS backends.json INODE BACKEND`。固定线性一致查询观察到的当前版本，只接受该版本声明的非零目标后端。目标对象库必须已经存在，不初始化目录；目标对象若已通过完整校验，返回 already_healthy。对象缺失时，从其他已声明位置选择健康副本，复用上传的 staging、复制校验、fsync、读回校验和原子不覆盖安装流程。

返回 JSON 包含 inode、version、backend、source_backend 和 status。执行补齐后为 repaired，已健康的无操作结果为 already_healthy 且 source_backend 为 null；repaired 也可能是并发修复已安装相同对象后校验成功。所有副本均不可用、配置缺失、目标库不可访问或目标对象损坏时命令失败，保留现有对象。发生安装后错误时可能留下有效对象，可安全重试。

修复不提交元数据，不改变版本声明、副本策略或命名空间。并发发布或删除可能使固定版本成为历史版本，但不会将其重新发布或复活文件。当前仅支持缺失对象补齐，不支持损坏对象替换、自动调度、增加副本位置或 GC 协调；后端挂载身份仍依赖配置，NAS I/O 尚无截止时间。

真实 Samba/CIFS E2E 覆盖双请求并发补齐、健康目标重试、空对象补齐、无健康源时失败、目标路径缺失不创建、未声明后端拒绝、损坏对象和符号链接保留，并验证版本记录及当前版本未改变。后端服务重启与重新挂载后继续检查对象哈希。

## 27. 显式可写 SMB/FUSE 原型

挂载增加 `--write-backends 1,2`，显式选择两个已登记、不同故障域且本地对象库已存在的后端。启动检查配置、故障域及 canonical root 不重复，不自动初始化目录。Samba 工具增加 `--writable`，仅允许导出可写 nas-fs 挂载；默认仍为只读。实验部署使用一个可写入口，其余入口只读，尚无全局写者选举、跨节点 share-mode 或自动写者故障迁移。

实现 create、mkdir、open/write、大小截断、非覆盖 rename/move、unlink 和 rmdir。可写挂载目录/文件权限为 0755/0644，新建对象明确使用双副本策略；已有单副本策略文件拒绝写打开。元数据新增 rename_entry/remove_entry，将名字解析和变更放在同一 Raft 应用事务中；remove_entry 校验文件/目录类型，禁止删除非空目录，rename 不覆盖已有目标。请求去重防止重放删除名字被复用的新文件。LMDB 与内存参考模型都实现并验证重启/快照一致性。使用新命令前需整体升级元数据节点，旧程序无法解析对应 WAL 命令。

写句柄使用 libc tmpfile 创建匿名本地暂存文件，从完整校验的当前副本复制初始内容，记录 expected_version。同一挂载内每个 inode 只允许一个写句柄，第二个返回 EBUSY。每次 FUSE write 或大小变更都同步复制完整结果到两个后端，经过大小/SHA-256 校验、文件同步、读回和原子不覆盖安装、目录同步后，再 CAS 发布不可变版本；成功完成才回复该次写入。新建文件先发布双副本空版本，再回复创建成功。flush/fsync 不重复发布，只报告句柄状态。已有读句柄仍固定旧版本。

这是按次写入提交的正确性原型，不是整个上传原子替换：上传中的已提交中间版本对新读者可见，覆盖可先发布空截断版本。每次都复制整文件，写入放大与延迟显著。当前保留版本上限 2048、请求收据上限 8192，每次写入都消耗配额，不能用于长期大规模写入。后续可在明确 flush/close 语义后优化合并提交。

第二副本失败时不发布该次新版本。任何写入/发布失败都会冻结该写句柄，后续读写及 flush/fsync 返回错误，close 也可能报错；不继续改写其暂存内容或提交另一请求。外部 CLI 或其他挂载先发布新版本时，旧 expected_version 的 CAS 失败返回 EAGAIN，不能覆盖胜出版本。这不等于跨节点 SMB 锁协调。RPC 错误可能隐藏已提交结果，应重新打开并查询当前版本；失败创建可能留下未发布 inode，失败发布可能留下孤儿对象，不自动删除。进程退出清理匿名本地暂存，已确认写入不依赖该暂存恢复。

Samba 关闭 DOS archive 位映射和 DOS xattr 存储，保留 strict sync。尚不支持持久时间戳、chmod/chown、ACL、链接、rename 覆盖已有目标、mmap 和 durable SMB 会话恢复。后端挂载身份仍依赖管理员配置，NASFS-5 的掉挂误写防护未完成，不能将此原型视为生产可写服务。

测试扩展：真实可写 FUSE 的双副本检查、偏移写、截断/覆盖、旧读句柄、写句柄互斥、第二后端失败、CLI 并发发布冲突、跨目录移动/重名拒绝、打开后删除和非空目录拒绝；完整 SMB E2E 增加上传、覆盖、下载、改名、删除、建/删目录、空文件、第二副本失败及元数据 leader 恢复后的写入，同时保留全部只读回归和后端重启/重挂哈希检查。

## 28. 显式损坏副本原子恢复

`repair-file ENDPOINTS CONFIG INODE BACKEND --replace-corrupt` 扩展第 26 节的缺失副本补齐。默认行为仍拒绝损坏目标；只有显式开启时，目标完整校验返回 ChecksumMismatch 才允许替换。对象库不可访问、类型异常、符号链接或其他校验错误不作为损坏替换的授权条件。没有健康源时保留原目标并失败。

恢复固定一个不可变版本，从其他声明位置选择完整校验的健康源，在目标 staging 创建独占随机文件，复制过程中核对大小/哈希、同步文件并读回校验。先尝试不覆盖安装；已有目标则再次完整校验。如果并发修复已使其健康，保留并同步该对象；仍为 checksum mismatch 时，对同一版本对象名执行原子 rename 替换，最后同步 objects 与 staging 目录。所有正常安装者都必须为该版本名字提供相同大小和 SHA-256 的内容，并发修复因此收敛到等价字节。普通上传与 SMB 写入仍使用不覆盖路径。

替换不修改旧 inode，已有描述符继续引用原对象，包括损坏内容或截断错误；只有重新打开才获取修复副本。FUSE 不在旧句柄内切换对象。恢复不写元数据，不改变版本 ID、当前版本或命名空间；并发发布/删除不会被修复重新发布或复活。当前不保留坏对象归档；崩溃可能留下 staging 或已安装对象，正常错误清理 staging，安装后结果不确定可重试检查。

32 项单测包括源内容变更时拒绝安装并保留坏目标、默认 put 不替换、修复后重复执行和旧描述符保留。真实 Samba/CIFS + FUSE Safe E2E 覆盖并发损坏修复、全损坏时拒绝、符号链接保留、空文件恢复、元数据不变，以及旧 FUSE 句柄仍报 EIO、新打开读取正确数据；后端重启/重新挂载后检查全部对象哈希。精确崩溃时点注入、与未来 GC 的协调及物理 NAS 断电验收仍待补充。

## 29. 修复进程崩溃与命名空间竞态验收

新增显式构建选项 `-Dfault-injection=true`，仅测试构建读取 NAS_FS_REPAIR_STOP 并在 before_replace、after_replace、after_sync 检查点发出 SIGSTOP。普通构建编译掉检查点，不读取该变量。测试通过 waitpid(WUNTRACED) 确认到达位置后 SIGKILL 或恢复执行，避免依赖拷贝速度猜测崩溃时机。入口为 `zig build test-cluster -Dfault-injection=true` 和 `zig build test-e2e -Dfault-injection=true -Doptimize=safe`；参数贯穿私有挂载 namespace 与集群测试进程。

真实 Samba/CIFS 故障验收覆盖替换前、替换后、目录同步后杀进程。替换前仍保留坏对象和一份已校验 staging；替换后可观察到健康对象，三个场景重试后均恢复双副本健康且元数据不变。测试只清理自身识别的 staging 孤儿，生产修复不增加自动 GC。重试遇到 already_healthy 时现在仍同步对象文件和 objects/staging 目录，补齐上次可能尚未完成的目录同步，而不简单以哈希正确代替同步完成。

另外在替换前暂停修复，分别发布新版本、删除旧 inode 并复用同名新文件、由另一进程先修复目标。恢复执行后只修复已固定版本的对象：不回滚当前版本，不复活旧 inode，也不改变同名新文件；并发健康替换保持字节等价，原健康描述符继续可读。上述验证补齐第 28 节的精确进程崩溃与竞态场景，不等价于 NAS 掉电耐久性、后台自动修复或未来 GC 协调。

## 30. CIFS 挂载身份校验与本地回落防护

后端映射现在必须显式选择 mount 或 allow_local，二者互斥。NAS 配置示例：`{"id":1,"root":"/mnt/nas-a/nas-fs","mount":{"mountpoint":"/mnt/nas-a","source":"//192.0.2.10/data","address":"192.0.2.10"}}`。旧版仅 id/root 的配置返回 BackendIdentityRequired，需要补全。开发测试可用 `"allow_local":true` 显式允许普通目录，此模式不提供挂载身份或物理副本保证。

校验先打开 root 描述符，从 `/proc/self/fdinfo/FD` 读取 mnt_id，再匹配当前 namespace 的 `/proc/self/mountinfo`，要求该挂载仍可见、类型为 cifs、挂载点/UNC/addr 与配置一致、挂载 root 为 `/`。procfs 文件报告大小零，使用有界流式读取，不能依据 stat 大小读文件。路径转义按 mountinfo 八进制规则解码。校验失败在创建 import/staging/objects 之前返回；随后确认 staging 与 objects 的描述符属于同一挂载，拒绝嵌套本地挂载或另一文件系统。

上传、检查、普通/损坏修复、FUSE 读取和 SMB 写入共用映射打开路径。复制开始和安装前再次核验 root。路径被卸载后，新打开的本地目录不能通过 CIFS 身份检查；已打开描述符仍固定原文件系统，不能因路径复用转而写入宿主目录。若卸载恰好发生在检查后，在途 I/O 可能继续作用于原文件系统；该保证不等于全局 fencing 或立即取消全部在途 I/O。正确重新挂载后新的 mnt_id 可自动通过配置匹配，无需重写配置。

同一地址、同一共享名的多份映射直接拒绝，即使 UNC 主机别名或本地路径不同。Linux CIFS mountinfo 不暴露连接端口，因此不能用不同端口宣称同一 UNC/address 是不同后端；测试的两个 Samba 实例改为 data0/data1 不同共享名。物理 NAS 故障域仍需管理员正确登记，不把多个共享/IP 或本地目录当作独立硬件的证明，也不提供服务端身份认证。

真实 CIFS E2E 持有旧目录描述符后 lazy-unmount，创建同路径本地空目录，验证上传/修复失败且未创建任何对象子目录；随后挂错另一共享，验证即使内容恰好相同也拒绝写入；再正确重挂验证双副本健康恢复。额外把本地目录 bind 到 staging，验证跨挂载子目录拒绝且没有本地写入。上述异常均验证读取回退到另一副本、版本元数据不变，另覆盖重复/缺失身份拒绝。Safe 完整 SMB E2E 保留只读、同步双副本写入、修复、故障切换与重挂哈希回归。

本轮并发修复回归发现：另一修复原子替换目标会改变旧 inode 的 ctime，使正在校验它的请求得到 SourceChanged。仅修复目标增加一次重新打开/完整校验，避免把并发成功替换误判为持续故障；复制源变化仍然失败，不放宽源校验。

## 31. 可写入口崩溃与客户端断连验收

以 `zig build test-smb -Dfuse=true -Dfault-injection=true -Doptimize=safe` 运行真实 CIFS 后端、FUSE 接入和 Linux smbclient。仅测试构建识别 NAS_FS_WRITE_STOP，提供 first_replica、both_replicas、published 三个非空文件发布检查点；正常构建不读取该变量。测试用 waitpid(WUNTRACED) 确认接入进程已 SIGSTOP，再精确执行 SIGKILL，不依赖睡眠猜测发布时机。

直接 FUSE 写入与 SMB 上传分别覆盖三个检查点，共六个崩溃场景。检查各后端安装对象的数量、字节与版本标识、元数据是否已发布、客户端没有错误地报告成功、只读入口可见内容，以及新建可写入口能继续 CAS 发布健康双副本。发布前崩溃保留此前已提交版本；SMB 覆盖先独立提交空截断，因此该情况下保留空文件，而直接偏移写保留原内容。元数据已提交但回复前崩溃时，新内容已可见，即使客户端报告失败。未引用对象保留，仍由未来 GC 处理。

另在第一副本完成时杀掉 smbclient，再 SIGCONT 恢复接入进程，验证在途写请求仍完成双副本发布，之后只读可见且重启可继续写入。客户端断连不是取消或回滚保证，失败/无确认不能推断未提交；应重新打开并检查实际版本后再决定重试。这些测试不提供整个上传原子替换，也不替代 Windows/macOS 客户端验收、分布式锁或 NAS 掉电测试。

测试基础设施记录挂载成功状态，即使接入进程 SIGKILL 后 ismount() 返回 false 也执行卸载；Samba 使用短状态目录，并在启动失败时附带内部日志。Safe 完整 SMB 故障套件通过上述七个场景及既有修复、挂载身份、集群恢复回归。

## 32. 在途写入跨元数据 leader 切换

在前述故障套件中增加直接 FUSE 与 SMB 两个场景：写请求完成两个对象副本后，在发送元数据发布 RPC 前 SIGSTOP 接入进程。核验两个对象字节及版本 ID 一致、版本尚未进入元数据，然后 SIGKILL 当前元数据 leader，等待剩余两个 voter 选出不同 leader。此时再次确认 inode 的当前版本未变、暂存版本未发布，再 SIGCONT 恢复接入进程。

客户端必须正常成功：直接 FUSE pwrite 返回完整长度，smbclient 成功退出且没有 NT_STATUS 错误。检查元数据当前版本恰好等于暂停前记录的对象版本，而非另一次写入产生的版本，并验证双副本健康。finally 恢复旧 voter，继续执行只读内容检查、接入进程重启和新写入验证。

Debug 与 Safe 的完整 `test-smb -Dfuse=true -Dfault-injection=true` 均通过，故障矩阵现含六个接入崩溃、一个客户端断连和两个在途 leader 切换场景。该新增覆盖点是发布 RPC 发出之前的选举，不等于 Raft 提交中选举或提交回复丢失与选举的组合故障；Windows/macOS 客户端与部署恢复验收仍待完成。

## 33. 双副本落盘后失去元数据多数派

为直接 FUSE 和 SMB 各增加一个场景：在 both_replicas 检查点暂停，核验两个对象副本的版本与字节一致，且版本尚未进入元数据；保留当前 leader，SIGKILL 另外两个 voter 后恢复接入进程。必须保持多数派不可用直到客户端返回失败，直接 FUSE 不得输出 WRITE_ACK，SMB 必须以失败退出或报告 NT_STATUS 错误；接入进程仍须存活。随后才在 finally 中启动停掉的 voter。

恢复多数派并选出 leader 后，线性化读取实际 current_version，只接受此前版本或暂停前记录的待发布版本，拒绝第三种结果。如果仍是此前版本，待发布版本不得出现在元数据；如果待发布版本已提交，则按新内容验证。继续检查只读入口完整内容、双副本健康和接入重启后的新写入。

Debug 与 Safe 完整 SMB 故障套件均通过，矩阵增至十一例。两个构建的直接 FUSE 场景均观察到：客户端已收到失败，恢复多数派后原请求仍提交。其原因是无成功确认不等于日志提案撤销，超时提案可能在多数派恢复后提交；这不是无多数派提交，也不是假成功。两个对象副本完成只满足数据阶段条件，不能单独成为客户端成功依据。恢复流程必须检查实际版本，不能盲目假定失败操作已回滚。

## 34. 提交回复丢失与 leader 切换后的原请求重放

测试构建新增元数据服务端检查点：成功的非空 publish 已应用、准备返回 RPC 回复时，读取 NAS_FS_PUBLISH_STOP_DIR 指定目录中以 inode 命名的一次性标记。原子消费标记后记录 inode 与原 request_id，再 SIGSTOP 整个服务端进程。正常构建不读取该变量或执行检查点；空截断不会触发。

FUSE 和 SMB 各增加一例：先在双副本落盘后暂停接入进程，再放置 inode 标记并恢复接入请求；通过 waitpid(WUNTRACED) 确认服务端已停在提交后的回复前检查点，捕获原请求 ID，杀掉该 leader，等待另一 voter 成为 leader。原 leader 保持停止直至重放验证结束，保证请求由剩余 voter 处理。

自动重试有预算上限，实际测试曾遇到 ClusterUnavailable，因此本场景不承诺客户端一定透明成功。无论自动重试成功还是明确失败，都在新 leader 上以原 request_id、原 expected_version 和相同 publication 重放。必须返回原来的 ok/inode 回执，current_version 必须保持为暂停前的对象版本；不能因为 expected_version 已过期而将重复请求误判为版本冲突。随后校验完整内容、健康双副本及接入重启后继续写入，最后恢复旧 voter。

Debug 与 Safe 完整 SMB 故障套件通过，矩阵增至十三例；35 项单测通过，普通 Safe FUSE 构建检查确认不含三类故障选择器。另为 FUSE 发布失败增加 inode、expected_version 和错误名日志，帮助定位不确定结果。重放原请求的幂等性不等于普通 SMB 客户端重新打开并重写会复用同一 request_id，也不等于会话透明恢复；部署恢复与 Windows/macOS 验收仍待完成。

## 38. 后端双 staging 写会话

可写句柄直接持有两个 NAS staging 文件，不再使用接入机 tmpfile。普通 write/truncate 顺序修改两侧，成功表示两侧接受修改，不表示已同步或发布。新建与截断打开从空 staging 开始；局部修改先从完整校验的旧版本用 256 KiB 缓冲区复制到两侧，尚无 reflink、服务端复制或并行写优化。

flush/fsync/关闭遇到脏句柄时，重新验证配置目录与固定描述符的挂载 ID/inode，分别同步并计算摘要，要求大小和哈希一致，再以不覆盖 rename 安装两个不可变对象、同步目录，最后 expected_version CAS 发布。O_SYNC/O_DSYNC 写入在回复前执行发布。重复 fsync 无新修改时不创建版本；发布消耗可写 staging 描述符，同一句柄后续修改重新建立 staging，不能原地修改已发布对象。

写句柄读取自己的 staging；其他读者读取已提交版本，已打开只读句柄固定旧版本。未发布的新 inode 可以先出现在命名空间，但尚无可读版本。flush（包括继承描述符关闭）可能在上传中途触发，因此仍不保证整个 SMB 上传原子替换。任何写入或发布失败冻结句柄；CAS 冲突不覆盖其他发布。RPC 错误可能隐藏已提交结果，必须保留已安装对象并查询实际状态。

进程死亡可能留下孤立 staging；已确认普通 write、尚未发布的数据不自动恢复，也没有 staging GC 或跨机写会话 fencing。发布后的耐久性仍依赖 NAS 对 fsync 的实现，不以进程崩溃测试代替硬件断电验证。单可写入口建议和版本/回执容量限制仍适用。

新增单元测试验证 staging 重命名保持 inode、后续 staging 不改变不可变对象，以及配置目录被替换时拒绝写入。FUSE/真实 CIFS SMB 验证双 staging 内容与未发布可见性、重复 fsync、同句柄多次提交、稀疏写/截断、staging 损坏冻结和 O_DSYNC。故障矩阵扩展为十五项：新增在首侧 staging 写完后杀死接入进程，以及双侧普通 write 已确认、fsync 前杀死进程；均验证未安装对象、元数据保持旧版本、重启读取原内容，明确区分 WRITE_ACK 与 COMMIT_ACK。

## 39. 已确认的后续方向：双副本 redo WAL 与完整文件原地更新

用户已接受取消“已打开读句柄始终读取旧版本”的保证，改为普通可变文件语义。NAS 上仍保留完整文件，不使用分块内容布局。目标是消除局部修改和反复 fsync 引起的整文件复制；当前第 38 节实现尚未切换。

### 39.1 写入与持久边界

- 同一文件的 write/truncate/fsync 必须排序；两侧独立 I/O 并行发起，并在两侧操作都结束后返回或冻结句柄，不能遗留未收束的后台写入。
- 在修改数据前，将包含精确文件身份、写入代次、序号、操作类型、偏移/长度、数据和校验的 redo 记录写到两侧 NAS WAL，并同步两侧。WAL 不能只存在接入机。
- WAL 持久后才原地更新两侧完整文件；两侧数据写完成后确认普通 write。其恢复保证依赖持久 WAL，不等于数据文件已经 fsync。
- fsync 同步两侧数据文件，持久化安全检查点后才允许回收所覆盖的 WAL。O_SYNC/O_DSYNC 在回复前完成对应同步边界。检查点与元数据大小/代次更新的先后顺序必须在实现协议中明确。
- 使用 redo 向前恢复，不承诺失败请求回滚；未收到成功的请求也可能在恢复时生效。truncate 必须先记日志，不能先缩短文件再补日志。

### 39.2 读取与故障协调

取消固定旧版本不等于允许读取副本失配或绕过恢复状态。读取需与同文件写入协调；一侧失败后标记文件需要恢复，不能把落后的副本当作健康副本任意切换。启动及故障恢复先核对两侧日志、文件身份和检查点，按序重放，再开放访问。

第一阶段继续使用单可写入口；同机协调不能自动覆盖其他只读接入节点。启用原地更新前必须明确跨入口读屏障以及旧写入者排除机制，未完成时限制为单接入入口。Raft 代次或租约本身不能阻止旧进程继续向普通 SMB 文件写入，不允许仅以租约超时自动接管写入。

### 39.3 实现前必须闭合的协议与验收

日志格式必须能识别截断尾部、损坏记录和重放次序；两侧日志仅一侧持久、写入仅一侧完成、检查点推进中崩溃以及日志回收中崩溃均需确定恢复规则。明确单副本不可用时的拒绝服务边界，不能默默降低双副本保证。

当前 objects 文件名和版本元数据带整文件 SHA256，依赖不可变内容，不能直接在原对象上覆盖并继续使用旧摘要。需要新的可变文件身份、读取/修复校验协议和显式格式迁移；不在每次小写或 fsync 后重新扫描整个文件。校验元数据可以独立维护，但数据文件仍保持完整文件布局。

验收覆盖写入日志前后、首侧/双侧日志同步、首侧/双侧数据写、数据同步、检查点持久化和日志回收的故障窗口，以及重复重放、稀疏写、缩短后再扩展、读写并发和接入重启。增加大文件小范围反复修改加 fsync 的实际 I/O 计量，验证不再整文件复制；两份 WAL 加两份数据的逻辑写量约为修改字节的四倍，实际流量还取决于日志批量与存储实现。

## 40. WAL 数据层原型（尚未接入 FUSE）

新增 `src/file_wal.zig`，对调用方独占持有的双数据文件和双 WAL 描述符提供 recover/write/truncate/sync。数据文件原地修改，不创建整文件工作副本。双侧日志追加与同步、双侧数据写/截断、双侧数据同步均使用 Io.concurrent 并行执行；即使一侧失败也等待另一侧结束，之后冻结会话。运行时无法提供并发时返回错误，不静默退回顺序写。

日志记录为固定 112 字节头加最多 1 MiB payload，包含格式 magic、从 1 递增的序号、inode/generation、操作类型、offset、长度和 SHA256。头单独校验，避免损坏的长度伪装成未写完的 payload；整条记录另校验头字段和数据。每次修改先同步双 WAL，再修改双数据文件；sync 同步双数据文件但不删除 WAL。

恢复先完整校验两侧日志，公共字节必须一致，完整损坏、身份错误或序号错误均拒绝；只允许丢弃不完整的最终记录。采用较长的完整有效前缀，包括可能未确认的修改；将缺失后缀补到另一侧并同步双日志后才顺序重放。修复日志不重写已有有效前缀。重放 write/truncate 可重复执行，恢复完成前不开放访问。

本层要求调用方已经验证精确文件身份、同步目录项并排除并发访问；不能把丢失的数据文件/WAL 创建为空后传入恢复。日志只保存修改，不包含完整基线，无法独立重建未被覆盖的旧数据。调用方还需实现挂载重验证、所有权及跨入口读屏障、元数据大小/代次协议和旧格式迁移。

当前单侧日志上限 64 MiB，恢复最多读取双侧 128 MiB 日志到内存；达到上限时在写入前拒绝新修改。尚无检查点/日志回收，因此这是可验证的数据层原型，不是已经切换的 SMB 写路径。既有 CLI/FUSE 仍使用第 38 节 staging 实现。

Debug/Safe 各 47 项单元测试通过，其中新增 10 项覆盖：稀疏写、缩短再扩展、重复重放、单侧日志尾部逐字节截断、双侧不完整尾部、完整记录及长度损坏、错误代次、合法但分歧的日志、日志/数据单侧写错误后等待另一侧并冻结、既有基线保留、范围/容量拒绝。16 MiB 文件三次单字节修改加 sync 保持数据 inode 和大小，单侧日志只增长 339 字节；这是本地数据层验证，尚不是 CIFS 流量测量或进程 SIGKILL 的完整 SMB 验收。

## 41. 可变文件检查点、日志轮换与 CIFS 验证

新增 `src/file_store.zig` 管理每个逻辑文件专用的双后端目录，目录中 `data` 始终是完整普通文件，`wal-<起始序号>` 是当前或待回收日志，`checkpoint` 是带 SHA256 校验的 inode/generation、下一序号和数据大小。初始化只接受新文件；目录父项持久化和 NAS 映射校验仍由上层负责，初始化失败不自动覆盖已有文件。

检查点推进顺序：并行同步双数据文件 → 两侧创建并同步空的新代日志和目录 → 并行以临时文件写入/fsync/rename/目录 fsync 原子发布检查点 → 替换会话日志描述符。任何推进错误冻结会话，所有可能仍用于恢复的日志保留。重复 sync 无新修改不轮换；接近单代 64 MiB 上限时先建立检查点再继续写，文件生命周期写入量不再受单日志上限限制。

恢复先取得双数据文件非阻塞独占锁，再读取检查点。若只有一侧推进，以有效的较高检查点为准：它的发布前置条件已经包括双数据同步和双新日志持久化。当前日志必须实际存在，不能补建为空。重放当前代日志并同步数据，再使两侧检查点收敛。完整损坏的检查点、身份不符、同序号大小不同均拒绝；无待重放日志时还检查数据大小与基线一致。数据文件和 WAL 都不能凭“可恢复”推测而空建。

`collect` 在重新验证双侧检查点与会话一致后，仅删除序号严格小于当前代的规范命名日志，并同步目录；删除一半后中断可重试。当前代、未来代或不认识的文件不删除。检查点发布前遗留的同名空新日志可复用，非空则拒绝。回收是显式操作，sync 及容量轮换不会代替上层调用 collect；尚未完成元数据协议时，不将检查点等同于 Raft 元数据已更新。

独占锁覆盖整个文件会话，关闭/进程死亡释放。本地和实际 CIFS 竞争验证发现，flock 可能返回 EAGAIN 或 EACCES，两者都视为未取得独占访问权。该机制不替代断网后的跨接入节点 fencing，也没有验证 NAS 重启后旧会话锁恢复；原地写仍不得直接用于自动切主。

新增测试覆盖检查点单侧推进/真实发布错误、冻结后的恢复、半程回收、缺失当前 WAL、非空孤立新 WAL、检查点损坏、锁竞争、错误代次、基线大小错误、重复同步，以及累计超过 64 MiB 的自动轮换。独立 `zig build test-file-store [-Doptimize=safe]` 复用既有双 Samba/CIFS 私有 mount namespace，分别在普通写后、检查点后、回收后 SIGKILL，重新打开验证内容与数据 inode，并验证另一个进程被锁拒绝、Samba 重启和冷 CIFS 重挂后的恢复。故障 driver 是单独测试程序，不安装到产品 CLI。

验证结果：Debug/Safe 各 57 项单元测试通过，两种构建的独立双 CIFS 测试通过；既有 Safe 元数据/对象真实 CIFS E2E 回归通过。上述检查点单侧推进测试属于可控状态/错误注入，不声称已经覆盖 NAS 断电或所有 fsync 中间窗口。

目前这仍是独立可变文件数据层；SMB/FUSE 继续运行第 38 节的 staging 实现。后续需要接入元数据大小/代次与格式迁移、读写协调、守护挂载映射和修复校验协议，之后才能替换实际 SMB 写路径。

## 42. 可变文件绑定与持久检查点元数据

inode 新增可选 `mutable_file`，包含 generation、next_sequence、size 和两个 backend ID。它表示 Raft 已记录的持久检查点，不是正在写入文件的实时大小。不可变对象的 current_version 与此字段互斥，历史版本仍保留。

- `mutable_file.attach`：对 inode、expected_version 和尚未绑定可变文件的状态做 CAS。要求普通文件、双副本策略、非零代次/序号、合法大小，以及已登记的不同故障域。成功后记录可变文件身份并清除 current_version；不复制文件、不删除旧版本，也不允许再次绑定来隐式替换身份。
- `mutable_file.checkpoint`：校验 generation 与 expected_sequence，允许跳过多条 WAL 更新到更高 next_sequence，也允许相同序号/相同大小的幂等状态声明；拒绝序号倒退或相同序号改变大小。只更新现有 inode，不新增不可变版本。
- 原请求 ID 重放继续返回原回执，即使文件后来又推进；用新请求 ID 提交过期 expected_sequence 则返回 sequence_conflict。更新、回执和 applied cursor 仍在同一 LMDB 事务中。
- 已绑定可变文件拒绝不可变 publish 和切换为单副本；目录改名、移动和移除沿用原协议，移除不会自动删除后端文件。

调用方必须先持有双侧数据访问权，完成文件初始化/迁移与数据检查点，再提交元数据。若进程在数据检查点后、元数据更新前退出，恢复后核对同一代次并以当前元数据序号 CAS 推进；如果 RPC 结果不确定，复用原请求 ID 或读取实际状态，不将数据回滚。单测已串联真实 file_store 与 LMDB，验证此恢复窗口、回执重放及不新增 versions 记录。raw apply 只校验声明，不能证明后端存在、内容正确或锁已取得。

LMDB schema 与快照输出升级到 3；可读取 schema 1/2 和版本 1/2 快照，缺少 mutable_file 默认 null，保留旧命名空间/发布请求摘要与回执。必须整体升级元数据节点，不支持混合版本或降级。新增状态经过内存/LMDB 状态机逐步对比、每步关闭重开和快照替换测试，并验证旧格式升级与非法可变快照拒绝。

真实三 voter 测试验证：绑定和检查点在 leader 被杀后可重放，两个并发检查点 CAS 仅一个成功，旧回执不覆盖新检查点，整个集群 SIGKILL/重启、落后节点快照追赶及删除本地 LMDB 后重建仍保留相同状态。Debug/Safe 各 61 项单元测试及 Safe 三节点套件通过。

本轮没有把元数据更新误当成读写屏障：跨入口读协调、写入所有权协议和实际迁移尚未接入。现有 FUSE/对象 CLI 对可变文件内容明确返回不支持，避免当成未发布空文件或继续走 staging；SMB 默认仍为原实现。请求回执容量上限仍为 8192，元数据检查点不消耗版本槽，但没有解决回执回收。

## 43. 守护访问会话、迁移与真实元数据补报

新增 `mutable_access.Access` 连接映射校验、完整可变文件、WAL 与元数据协议，`mutable_rpc.Client` 使用现有 leader-aware RPC/ReadIndex 和保留原始请求内容的有限重试。元数据接口返回不借用 inode 名称的值类型，调用方持有配置和 RPC client 的生命周期，并串行调用同一 Access；没有后台未收束 I/O。

首次迁移先读取 inode 和已登记故障域，验证双副本策略及本机映射，在各 root 下创建 `mutable/<inode>-<generation>/`。从一个完整校验的旧不可变副本以 256 KiB 缓冲区复制，通过双 WAL 写入完整 data 文件；迁移结束校验两侧完整内容、同步数据检查点，再以 expected_version CAS 绑定。新 inode 从空数据文件开始。旧对象不修改、不删除；初始化/迁移/CAS 失败可能保留未绑定目录，尚无这类孤立目录 GC。复制和整文件读回仅用于首次迁移，后续偏移写不复制整文件。

已有可变文件按元数据中的 generation/backends 打开；取得双侧数据独占锁后恢复当前 WAL。服务前验证元数据没有领先于本地已恢复序号，推进数据检查点并 CAS 补报领先于元数据的序号与大小。绑定或检查点的 RPC 回复丢失时保留数据，冻结当前会话；重新打开先查询实际绑定，不重新初始化已绑定代次。显式 collect 先完成数据与元数据同步，再回收旧代日志。

读、写、截断、同步与回收共用会话；普通 read 读取当前完整 data 文件的字节，不固定旧版本。每次访问前重新查询 inode 身份，重新验证配置 root、mutable 父目录、代次目录的挂载 ID/inode，以及 data 路径与固定描述符 inode；I/O 后再次校验映射。替换目录、数据文件、元数据不可用或 CAS 失败均冻结会话，后续操作不继续使用旧描述符。校验不等于对管理员并发修改目录的原子隔离，后端对象目录仍属于可信管理范围。

当前所有访问（包括读取）要求双侧独占所有权，其他 Access 打开同一文件返回 FileBusy；同一入口多个应用句柄需要在后续 FUSE 层共享同一个 Access。暂不提供跨进程共享读会话、锁丢失自动接管或断网 fencing；每次 I/O 的元数据查询也尚未做缓存优化。新可变数据的持续内容校验/损坏副本修复协议仍待完成，本层不将“路径身份正确”声称为“内容已经校验”。

新增 8 项单元测试覆盖迁移与旧对象保留、重复修改的 data inode 保持、独占访问、仅 WAL 已确认后的重开补报、绑定/检查点回复丢失、目录/data 替换冻结、元数据不可用和失败迁移。Debug/Safe 各 69 项单元测试通过。

独立 `zig build test-mutable-access [-Doptimize=safe]` 同时启动真实三 voter 与双 CIFS，使用产品 RPC 进行迁移绑定和检查点补报，分别在 write/checkpoint/collect 后 SIGKILL，验证竞争访问拒绝、恢复内容和大小、数据 inode 不变以及旧对象集合保留；write 场景还杀死当前 leader 后恢复访问。Debug/Safe 均通过；Debug 增加冷 CIFS 重挂后读取可变 data 内容和检查已回收日志数量。测试 driver 不安装到产品 CLI。

SMB/FUSE 尚未切换到此访问会话。下一步需要接入多句柄共享、可变文件实时大小、关闭/flush 错误传播及兼容的显式启用入口，随后验证实际 SMB 写路径。

## 44. 显式 WAL FUSE/SMB 入口与共享句柄

`mount --write-mode staging|wal` 和 `serve_access.py --write-mode` 提供显式选择，默认 staging；WAL 要求同时配置双 write-backends。FUSE Client 按 inode 保存引用计数 Shared，每个文件句柄包装同一个 Access，最后释放时关闭双侧锁。首次只读打开也执行迁移；已绑定文件的 lookup/getattr 会临时获取会话以恢复数据并查询实时大小。默认 staging 挂载仍拒绝可变内容，不将其误读为空文件。

WAL read/write/truncate 直接委托 Access；read/getattr 刷新大小，禁用文件页缓存以避免旧字节或旧长度。flush/fsync/release 调用 collect，先同步数据和元数据再删除旧日志；只读句柄也参与同步，后端错误冻结所有共享句柄。CIFS 目录缓存可能重复返回已删除旧日志，collect 对确认属于旧序号的 FileNotFound 容忍，其他错误仍失败。只读 O_TRUNC 在创建会话前拒绝，避免拒绝打开时已经截断内容。

本轮保留每 inode 一个可写句柄限制，多个只读句柄可与它共享；本挂载仍有会话时 unlink 返回 EBUSY，避免删除后 Access 身份检查失败。其他进程/挂载不共享该表，仍通过双侧独占锁拒绝竞争访问；这不构成跨节点 fencing，外部元数据删除也不受本地 unlink 检查保护。每次 I/O 查询元数据和验证路径的保守策略保持不变。

新增 test-wal-fuse/test-wal-smb：覆盖首次迁移、读写共享、stat/fstat 实时大小、稀疏写、ftruncate/O_TRUNC、重复 fsync、O_DSYNC、历史对象保留与 data inode 不变；验证第二写者、竞争挂载、活动句柄删除被拒绝。后端路径替换使所有共享句柄冻结，恢复后必须重开。独立子进程 write 成功后 SIGSTOP，杀死 FUSE 再恢复子进程，其 fsync 必须失败；新挂载重放 WAL，检查内容和 Raft 大小补报。

真实 SMB 测试覆盖上传、覆盖、下载、空文件、目录、rename/delete；supervisor WAL 参数转发、ready 状态及干净退出亦有覆盖。Debug/Safe 各 69 项单测通过；本地 WAL FUSE、双 CIFS WAL SMB 均有 Debug/Safe 验证，最终 Safe 包含 supervisor 验证；默认 staging 的完整 Safe SMB 回归通过。仍待后续完成可变内容校验/修复、跨节点 fencing、孤立迁移目录 GC，以及独立机器和 Windows/macOS 客户端验收。

## 45. 可变副本读取比对与全文件巡检

Access.read 不再只读取第一副本：先比对双侧长度，再用固定 64 KiB 辅助缓冲比对请求范围内的字节；大请求逐段处理，调用方只有在整个请求成功后才能使用返回数据。任意一侧读取失败、长度不等或字节不同都冻结 Access，FUSE 将错误映射为 EIO，后续共享句柄不能继续读写、同步或回收日志。Access.size 也比对双侧长度，避免 FUSE 根据第一副本的 EOF 提前返回空读而漏掉另一侧的扩展。成本是每次读访问两侧 NAS；不增加整文件 COW 或数据分块布局。

Access.scrub 在现有双侧独占锁和调用方串行化约束下，使用两个固定 64 KiB 缓冲比对完整文件并流式计算 SHA-256，检查大小、路径和元数据身份。巡检本身不 checkpoint、不 collect、不选择修复来源。返回 size、next_sequence 和观察到的摘要；SHA-256 未写入检查点或 Raft，不能作为未来自动修复的权威依据。

新增产品命令 `scrub-mutable ENDPOINTS CONFIG INODE`，只接受已有绑定，不迁移不可变 inode；复用 Access.open 的正常恢复流程后执行全文件比对。打开阶段可能重放 WAL、同步数据和补报元数据，因此不宣称整个 CLI 只读。输出 generation、序号、大小、replicas_equal 和十六进制摘要，失败非零退出；其他访问进程持锁时返回 FileBusy。普通读取只检测请求范围；显式巡检负责其余区域。

新增四项单测覆盖任一副本损坏时冻结和保留 WAL/元数据、长度不一致、空文件/跨 64 KiB 边界/稀疏尾部/EOF、大请求、巡检不推进检查点，以及明确记录“双侧相同损坏仍会一致”的能力边界。Debug/Safe 各 73 项通过。扩展 WAL E2E：本地 Debug FUSE 和 Safe 双 CIFS/真实 SMB 均通过，校验巡检 JSON 摘要、拒绝不可变文件迁移和竞争所有者；分别直接篡改两台 NAS 的 data，验证两个共享读句柄失败、CLI 报错且损坏与未损坏副本均保留，仅测试夹具恢复注入字节后重开。

自动修复仍需要新的持久内容证据协议：可信摘要必须与 generation/sequence 绑定，并处理原地写入期间摘要与数据非原子更新、WAL 重放和截断后的有效范围；恢复不能把两个当前不一致的副本任意选一个当正确源。仅把现有 checkpoint 的头部校验和当内容校验，或在 fsync 时给当下字节重新计算摘要，都不能补足这项保证。后续在保留完整 NAS 文件布局的前提下实现该协议及中断修复恢复测试。

## 46. 静止文件内容基线、写前失效与显式原地修复

本轮实现可选静止文件基线，避免给每次普通 fsync 增加全文件扫描。`file_seal.Seal` 是代次目录下独立的 104 字节 `seal` 文件：magic、inode、generation、checkpoint next、size、内容 SHA-256，最后附带前 72 字节的 SHA-256 校验和。数据继续是完整普通文件；Raft 元数据和 72 字节 checkpoint 格式不变。该校验和检测意外损坏，不抵御有权限修改后端的攻击者。

显式 seal-mutable 获取双侧 data 独占锁，复用正常恢复和映射检查；若已有基线，先验证它，不能以当前一致但已损坏的字节覆盖旧基线。同步数据并旋转检查点后扫描双侧完整内容，要求大小和摘要一致，再分别通过临时文件写入/fsync/rename/目录 fsync 发布基线，最后完成元数据检查点补报。首次基线承认当前一致内容，不证明之前历史正确。单侧发布中断时另一侧有效基线可以继续使用；两侧都有但不一致或任一侧结构损坏时失败关闭。

Store.write/truncate 在追加任何 redo 或修改 data 前，若持有基线，先顺序删除两侧 seal 并同步各自目录。仅全部成功后清除内存基线并继续写；失败冻结会话。删除中断只可能留下一个仍适用的基线，因为该阶段尚未追加 WAL/写 data；两侧都删除后即使崩溃也只丢失可选保护，不会把旧摘要用于新内容。零长度 write 不修改数据，也不使基线失效。无基线的普通写不增加 seal 目录同步，普通 fsync 不自动建立新基线。

打开已有基线时先检查其身份、序号和大小必须匹配选定 checkpoint，并要求双侧当前 WAL 均为空，然后验证两侧完整数据摘要，之后才进入正常 WAL 恢复。pending WAL 与 seal 共存返回 SealWithPendingWal，防止旧写者或外部恢复遗留摘要被误用。Access.scrub 除双侧比对外还验证已加载基线；普通范围 read 在会话内仍只比对两侧字节，不声称能检测之后发生的双侧相同修改。封存文件首次打开和临时 lookup 会有全文件扫描成本。

repair-mutable 在双侧独占锁下读取有效基线，只在至少一侧完整内容匹配时修复另一侧；两侧都匹配不复制，都不匹配返回 NoVerifiedReplica。先检查数据 checkpoint 不得落后于读取到的 Raft 序号。使用固定 256 KiB 缓冲原地覆盖目标，再设置目标长度、fsync，并重新校验源与目标；目标 inode 与其锁保持不变，源文件和基线不改写。中断后目标可能部分恢复，但源和基线仍可用于重试，普通打开在修复完成前拒绝服务。缺失 data、离线后端和无法读取/锁定的文件尚不支持重建；不存在基线时不进行猜测性修复。

新增 8 项单测，Debug/Safe 各 81 项通过：任一侧修复、长度缩减和 inode 保留、双侧相同损坏拒绝修复/重新封存、写入与 truncate 双侧失效、单侧发布/失效的中断状态、失效失败无 WAL/data 修改、无摘要/摘要损坏/身份和序号冲突/元数据领先/待回放 WAL 拒绝，以及部分修复状态重试和 Access 巡检冻结。本地 Debug WAL FUSE、Safe 双 CIFS/SMB E2E 通过：实际命令建立基线、任一 NAS 原地修复、两侧同损拒绝、写前删除基线后 SIGKILL 并按 WAL 恢复；原 SMB/supervisor 回归也通过。单侧发布/失效与修复中断采用构造磁盘中间状态验证，尚未进行修复复制中的真实 SIGKILL 或硬件掉电验收。

此协议提供显式静止文件保护，不是持续更新内容的可信校验体系。活跃写期间基线为空，仍需后续设计增量内容证据与 WAL 的关联，才能在任意写入阶段可靠自动修复。所有访问程序须支持写前基线失效，不混用旧版；跨节点 fencing、外部管理员并发修改隔离和独立机器验收仍未完成。

## 47. 静止文件修复过程的真实进程中断验收

复用既有 `-Dfault-injection=true` 和 `repair_fault`，新增 `mutable_first_chunk`、`mutable_synced` 两个确定性暂停点：前者在首个 256 KiB 已写入目标后，后者在完整复制、设置目标长度并 fsync 后、最终双侧摘要读回前。暂停点只在测试构建读取 `NAS_FS_REPAIR_STOP` 并 SIGSTOP；普通构建直接返回。修复算法和格式没有改变。

WAL FUSE/SMB 构建入口在启用故障注入时自动传 `--wal-faults`，测试使用超过三个复制缓冲长度的内容，把目标改为更长的损坏文件；分别以两侧作为目标，运行四种方向/时点组合。父进程通过 waitpid(WUNTRACED) 确认精确暂停位置，检查部分目标内容或已同步的完整内容，再 SIGKILL 并等待退出，避免以时间猜测复制进度。

每种组合验证：源数据始终完整；两侧 seal/checkpoint/各 WAL 的文件集合和字节保持；元数据绑定、序号和大小不变；暂停时竞争 scrub/repair 返回 FileBusy，FUSE 打开返回 EBUSY。首块后中断的目标仍不能通过正常巡检，目标同步后中断的文件可以通过巡检但命令没有向调用者报告成功；两种状态都可重跑 repair，并读回完整内容、保持两侧 data inode。

本地 Debug 与真实双 CIFS Safe 的四场景矩阵均通过，既有 WAL/SMB/supervisor 回归同时通过。启用故障注入的 Debug/Safe 单测各 81 项通过。另以正常 Safe 构建设置 `NAS_FS_REPAIR_STOP=mutable_first_chunk` 运行 WAL FUSE 套件，确认生产构建不会被测试环境变量暂停。fmt/diff 检查通过。

本节补齐第46节遗留的修复复制中真实 SIGKILL 验证；底层 NAS 和操作系统仍持续运行，因此不把该结果视为硬件掉电、控制器缓存丢失或断网 fencing 验收。seal 发布/失效窗口仍主要由构造磁盘中间状态的单测覆盖。

## 48. 基线发布与写前失效的真实进程中断验收

继续复用故障注入构建，在 seal 第一侧 publish 返回后、双侧 publish 返回后，以及第一侧删除并同步目录后、双侧删除并同步目录后增加确定性暂停点。后两处仍位于任何 redo 追加和 data 修改之前。正常构建直接跳过暂停，不改变发布与失效顺序。

新增 test_seal_faults，由已有 `--wal-faults` 驱动。两项发布场景暂停 seal-mutable 后 SIGKILL，验证 data/checkpoint/WAL 文件集合与字节、元数据及 data inode 不变，剩余一份或两份基线都能在重开时验证当前内容，重新封存成功。测试从已同步且未封存的文件开始，不混淆数据检查点推进与基线发布窗口。

四项失效场景分别对 write/truncate，在单侧或双侧目录同步完成后暂停并杀死专用 FUSE 进程。独立子进程执行系统调用，父进程确认调用尚未返回，同时从后端检查数据和 WAL 均未变化。进程被杀后调用必须失败；实际内核返回 ECONNABORTED，测试同样接受 EIO/ENOTCONN。单侧失效后残余摘要字节保持、重开仍是 sealed；双侧失效后重开是 unsealed，repair-mutable 返回 MissingSeal。之后从正常挂载重试修改，验证双侧内容、无遗留 seal、inode 保持，再显式建立新的匹配基线。

本地 Debug 和真实双 CIFS Safe 的六项场景通过，既有四项修复 SIGKILL、WAL/SMB/supervisor 套件继续通过。故障注入 Debug/Safe 各 81 项单测通过；正常 Safe 构建带 `NAS_FS_REPAIR_STOP=seal_first_invalidated` 运行 WAL FUSE 也通过，验证部署构建不受暂停变量影响。fmt/diff 检查通过。

本节补齐基线发布/失效关键持久边界的真实进程中断验证；没有模拟 NAS 同时断电、控制器丢缓存或目录 fsync 尚未完成时的硬件故障。活跃修改期间的持续内容证据和跨节点 fencing 仍未实现。

## 49. 当前 WAL 内容证据与检查点前核对

Store.sync 在双侧 data 同步后、创建新 WAL 和发布 checkpoint 之前调用 Session.verifyPending。重新读取双侧当前日志，要求字节完全一致，解析出的身份、序号、完整末尾及 next 必须精确匹配活跃会话；不接受恢复阶段才允许裁掉的未完成尾部。检查失败冻结会话，旧 checkpoint/WAL 和元数据不推进，避免把已损坏内容固化为新基线后删除唯一 redo 证据。没有待处理记录时也核对数据长度。

新增 wal_evidence.Evidence，从当前 checkpoint 大小出发按序处理记录。写入产生 payload 区间，越过 EOF 的间隙产生零区间；truncate 产生被截断或扩展范围的零区间，并更新逻辑大小。所有区间裁剪到最终 EOF。扫描排序后的区间边界，以最大操作索引优先的堆选择最后生效操作，从而正确处理覆盖、缩短后扩展和稀疏写，不把被后续写入覆盖的旧 payload 当作当前内容。索引计算为 O(记录数 log 记录数)，避免大量细小覆盖写的平方复杂度。

数据核对使用固定 64 KiB 缓冲，分别与两侧 data 比较，payload 借用已解析 WAL 的内存，不复制整文件。当前日志仍受 64 MiB 上限约束，读取两侧日志比较时的缓冲峰值最多约 128 MiB，随后释放第二份日志，再分配与记录数成正比的区间、事件和堆；这些索引是额外内存开销。读 I/O 与 WAL 大小及最终被覆盖的逻辑范围成正比，零区间也实际读取，因此大稀疏文件可能有较高 fsync 延迟。

真实 CIFS 测试发现 cache=none/actimeo=0 并不保证长期打开的可写描述符立即更新服务端被外部修改后的 st_size。核对除 stat 外还读取预期 EOF 前一字节和 EOF 位置，分别确认尾部存在和不存在额外尾巴；读取 WAL 也额外探测声明长度后的 EOF，防止缓存长度掩盖追加的日志尾部。这是失败关闭的核对，不声明能够对管理员并发修改提供原子隔离。

新增 7 项单测，Debug/Safe 各 88 项通过：任一/双侧 WAL 覆盖区损坏时保持 checkpoint/WAL 并重放恢复；1000 次覆盖写、截断和扩展与独立字节数组结果比对；空洞/扩展零区间损坏；双日志同时裁短、同损和分歧；未覆盖基线的能力边界；空日志下最终大小；以及 Access 失败后元数据不变、重开补报。没有改变 WAL/checkpoint/元数据格式。

本地 Debug FUSE 和真实双 CIFS Safe 套件新增五类端到端场景：独立子进程完成并确认写入后暂停，测试分别在两台 NAS 注入相同 payload 损坏、空洞非零、额外尾巴、文件变短和不完整 WAL 尾部，再恢复子进程。fsync 必须失败，checkpoint/WAL 保留且元数据不变；关闭后由正常打开重放并恢复完整内容。Safe 同时通过既有 SMB/supervisor 和十项 seal/修复 SIGKILL 场景，fmt/diff 检查通过。

本轮补的是检查点边界的内容证据：在 fsync 前，普通 read 仍以双侧字节一致性为准；未被当前 WAL 覆盖的基线区和 WAL 回收后的历史修改也不再由本机制证明。它不替代静止文件 seal，不构成持续的全文件可信摘要，也不实现跨节点 fencing。

## 50. 活跃 WAL 的读缓冲核对、大小查询与巡检

在第49节的检查点核对之上，Access.read 完成双侧读取比对后，向 Store.verifyRead 传入实际读取到的缓冲、offset 和原始请求长度。Session 复用精确双 WAL 校验和顺序解析，Evidence 将区间边界裁剪到请求窗口，直接核对已经填好的调用者缓冲，而不是再次读取 data 来替代它。短读长度须匹配 WAL 推导的 EOF。任意差异冻结会话，FUSE 不返回已经填入但验证失败的字节。

Access.size 用零长度验证请求检查 WAL 推导大小及 EOF 边界，避免 FUSE 根据错误的当前大小在进入 read 回调前直接返回空读；不扫描全部待写数据范围。Access.scrub 则先核对完整活跃 WAL 证据，再执行原有双侧全文件扫描与 seal 比对。干净会话的 read/size 不进入活跃 WAL 核对；checkpoint 和显式 scrub 仍执行各自的完整检查。

复用区间事件排序和最大操作索引堆处理请求窗口内的覆盖关系。尾部探测是额外的边界检查：若当前 WAL 覆盖逻辑 EOF 前一字节，按最后生效记录同时验证这个字节。真实 CIFS 曾在服务端截短文件后，依照已打开句柄的缓存长度把后续区域补零，使长度探测仍返回一个字节；内容校验成功拦截了本应非零的尾部被替换为零。对于本来就是零的后缀，客户端可见内容仍可能相同，本机制不据此证明服务端物理长度，也不提供外部修改的一致快照。

代价是有待提交记录时，每次 read/size 都重新读取双侧完整当前 WAL、校验并构建证据；请求窗口减少事件/数据范围，却不减少读取日志本身。FUSE read 可能先调用 size，再校验实际读缓冲，因而会重复日志 I/O。当前尚无可靠失效协议下的证据缓存，保留该保守行为并明确性能成本，不宣称实现完整的持续内容索引。未覆盖基线和 WAL 轮换后的内容仍依赖副本比对或显式 seal。

新增6项单测，Debug/Safe各94项通过：部分读跨重叠边界、未请求范围的普通内容损坏不误判、请求范围内双侧同损拒读；空洞/跨EOF/零长度请求；同损WAL拒读；dirty scrub识别同损；核对实际返回缓冲而非重新读取健康文件；以及stat尾部字节核对。调整原有能力边界测试，将“相同损坏无法发现”的场景明确放到 WAL 已轮换后的基线。

E2E矩阵由原5项fsync扩为13项：fsync/read分别覆盖payload、空洞、额外尾巴、缩短和不完整WAL尾部；stat覆盖两种长度损坏及WAL尾部。所有场景在未fsync的句柄上暂停注入相同双侧损坏，验证操作失败、checkpoint/WAL/元数据保持、重开重放成功。本地Debug和真实双CIFS Safe全部通过，既有SMB/supervisor及十项seal/修复SIGKILL继续通过。完整WAL故障套件因增加场景和核对成本超过旧600秒总时限，统一使用与既有SMB故障套件相同的900秒时限后通过；未放宽任何数据或失败断言。fmt/diff检查通过。

本轮未实现跨节点 fencing、自动写者接管或全文件持久增量摘要。活跃范围的读验证是当前 WAL 生命周期内的保护，不扩大到底层 NAS 独立故障域与硬件持久性的保证。

## 51. FUSE 单次读取去除重复大小预检

第50节的 FUSE read 回调先调用 size，再调用 read，两者都会重新读取双侧活跃 WAL。本轮将 C/Zig 的 read 回调增加实际字节数输出，Writer.read 对 WAL 直接返回 Access.read 已完成内容、长度和EOF核对的结果；C 层据此回复精确长度，并拒绝超过申请缓冲的返回值。

WAL read 不再独立查询大小，也不根据句柄保存的旧长度提前返回 EOF 或裁剪请求。一次 read 回调只走一次活跃日志证据核对，同时保留 1 MiB 单次缓冲上限、验证失败冻结和双侧数据比对。独立 getattr/stat/fstat 仍执行大小验证；内核或客户端另外发起的属性请求没有被缓存或省略。不把这个变化宣称为网络 I/O 总量减半。

staging 读继续按固定版本/暂存大小裁剪，提前 EOF 仍视为源内容改变；只是回调返回原有的确定字节数。未改变 WAL、checkpoint、元数据格式或静止文件基线协议，也未引入可靠性边界不明的内容索引缓存。

本地 Debug WAL FUSE、Safe 真实双 CIFS WAL 全部故障场景和默认 staging 完整 SMB 回归通过。增加旧读句柄在未先 stat 时看到扩展数据、跨 EOF 大请求短读、截断后 EOF 和大偏移空读断言；13项脏数据/WAL损坏场景、10项seal/修复SIGKILL及SMB/supervisor继续通过。C/Zig签名同时编译验证，fmt/diff检查通过。当前每个有效读取仍需要读取完整活跃日志，尚未完成吞吐性能验收。

## 52. 读窗口证据的流式验证与有界工作区

Session.verifyRead 不再复用检查点的整日志读取和区间排序。新增固定 64 KiB 预读 LogReader，连续读取两侧当前 WAL，避免每条短记录都单独发起文件读取；每侧最多分配一个 `header_size + max_write` 帧缓冲。先比较并认证头部、身份和序号，确认长度上限及剩余日志长度后才读取 payload，再检查两侧 payload 一致及完整记录校验和。末尾要求序号精确等于会话 next，且两侧预期 end 之后确为 EOF；活跃会话不接受不完整尾帧。

ReadEvidence 保留调用者实际返回缓冲的一份副本和可选的预期尾字节，从 checkpoint 大小开始顺序应用记录。仅将与请求窗口相交的 payload/零范围覆盖到副本，后续操作自然覆盖前面的预期值；未被 WAL 修改的窗口字节保留调用者原值，不伪称拥有基线内容证据。另以首次观察到的大小定位候选 EOF 字节，处理所有覆盖它的操作，最后要求推导出的逻辑大小等于观察值，复用 CIFS 边界和尾字节检查，再比较预期副本与实际返回缓冲。

该路径不持久缓存日志或解析结果；每次仍读取并认证全部双侧活跃日志，窗口外的校验和损坏同样失败关闭。读窗口、日志边界、截断后扩展、空洞及未覆盖基线的语义保持。检查点和全量 scrub 继续使用第49节的区间事件/堆算法，共享 EOF 与尾字节核对函数；它们仍需要整日志缓冲和与记录数成正比的索引。

read/size 的校验堆工作区上限约为两份 1 MiB 加 112 字节帧缓冲，加一份实际返回数据副本；另有两份 64 KiB 栈上预读缓冲。FUSE 单次 read 上限仍为 1 MiB，大小查询副本为空。记录解析是一趟顺序扫描，窗口预期值的 CPU 成本还取决于重叠覆盖次数和窗口长度，不能据去掉排序就宣称所有负载都更快。64 KiB 分块可能改变远端请求数量，总日志字节量没有减少。

## 62. 常驻核心的连接与共享句柄管理

目标入口调整为SMB3客户端→Samba薄C VFS→本机IPC→Zig常驻文件服务→内核CIFS→NAS。Raft仍只承载元数据。当前入口仍为Samba→FUSE；本节交付的是 `src/file_service.zig` 服务端会话管理层，尚未提供IPC监听器、常驻命令或Samba VFS模块。

显式关闭写句柄先sync，失败也释放该句柄并返回错误；幸存读句柄保留已冻结的Access，不因写者离开而跳过故障。断线清理不宣称fsync成功：释放该连接全部句柄，若尚有读者则继续共享原会话，否则关闭Access，下一次open按既有双WAL恢复协议重放并协调元数据。ID耗尽拒绝新分配，不回绕。deinit要求传输层已停止并join所有工作任务。
